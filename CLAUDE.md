# Reflectodoro

A Pomodoro app whose real point is forcing a short self-reflection ("what did I do?") at the end of every break, enforced via a hard-to-dismiss overlay. Ships as signed releases for **Windows, macOS, Linux, and Android** (see "Android" below); iOS is planned on the same stack but not yet started. The macOS build is currently unsigned/non-notarized (no Apple Developer account yet) and uses a best-effort media-pause toggle instead of Windows'/Linux's state-aware pause (the one macOS feature that needs a permission: Accessibility/post-event access). Alt-Tab/Win-key suppression is Windows-only plus X11-only-on-Linux — never on Linux-under-Wayland (a protocol-level limitation, not a scope cut), and has no equivalent on Android. macOS instead gets "kiosk mode" (`macos_overlay.rs`) — a different, permission-free mechanism (plain `NSWindowCollectionBehavior`/`NSApplicationPresentationOptions`, no Accessibility prompt) rather than a port of the Windows/Linux keyboard hook: blocking Cmd+Tab and keeping the overlay visible across every Space are always on, while hiding the menu bar/Dock is an opt-in Settings toggle, off by default — see "The overlay and its unlock formula", "Media pause-on-break", "Android", and "Not built yet / explicitly deferred" below. This build has no account/auth of any kind and no server or cloud service it depends on — every table lives in one local SQLite file per device. The one exception is **P2P LAN sync** (see below): a manual, opt-in, device-to-device feature that moves data directly between two paired devices on the same wifi network, with no third party or relay involved at any point.

## Keeping the landing page's development journey current

`docs/index.html` has a "Development journey" section: a vertical timeline (`.timeline`) summarizing real work from git history at **three tiers of granularity, newest first, that get coarser the further back you go**:

1. **Daily** — one `.timeline-entry` per calendar day, for each of the **last 7 calendar days** (today back 6 days) that has real commits. `.timeline-date` reads "*Weekday*, *Mon D*, YYYY" (e.g. "Friday, Sep 4, 2026").
2. **Weekly** — one `.timeline-entry` per ISO week (Monday–Sunday) for the **3 weeks immediately before** the daily tier's window. `.timeline-date` reads "Week of *start* &ndash; *end*, YYYY" (cross-month weeks read "Week of Aug 31 &ndash; Sep 6, 2026"; same-month weeks read just the day range plus one year, e.g. "Week of Aug 24 &ndash; 30, 2026").
3. **Monthly** — one `.timeline-entry` per calendar month for everything **before** the weekly tier's window. `.timeline-date` reads "*Month* YYYY" (e.g. "August 2026").

Each tier's entries sit under a `<p class="timeline-tier reveal">` label ("Last 7 days", "Previous 3 weeks", "Earlier" for the monthly tier) directly inside `.timeline`, in that order. **Omit a tier's label entirely if it has zero entries** (e.g. a young project has no monthly tier yet, as is currently the case here) — never render an empty placeholder.

**Whenever you make a commit (or a batch of commits in one session) that a user-facing changelog would care about** — new features, fixes, platform support changes, UI changes — update `docs/index.html` in the same session:

1. Recompute the tier boundaries from today's date (see the `currentDate` context): the last-7-days window, the 3 ISO weeks before it, and everything older than that.
2. **Aging out**: entries that have fallen out of a tier's window get folded into the next coarser tier rather than deleted — a day entry older than 7 days gets merged into its ISO week's weekly entry (removing the standalone day block); a weekly entry older than the 3-week window gets merged into its calendar month's monthly entry. When merging, theme-group the folded content into the coarser entry's existing bullets rather than concatenating lists — an entry should always read as one cohesive summary, never a per-commit or per-day log.
3. **Boundary week**: the ISO week containing the oldest day still in the daily tier will have some of its days already shown as their own day entries. Its weekly-tier bullets should summarize only the *other* days in that week (not duplicate what's already itemized under a day heading above) — but the `.timeline-date` label still shows the week's full Monday–Sunday range.
4. If today's commits belong to a day/week/month that already has a `.timeline-entry`, merge into it (same "fold by theme" rule as aging out). Otherwise insert a new `.timeline-entry` at the top of the relevant tier's block, with `class="timeline-entry reveal"` — `.reveal` is the page's scroll-in animation hook (its absence only skips the fade-in, it doesn't break anything).

Skip noise: "Bump version to X.Y.Z" commits and `Merge branch ...` commits are deliberately excluded — don't add them, and don't count them toward whether a day/week/month "has" activity. A day/week/month with no other commits gets no entry at all — never show a blank one.

Keep each entry to a handful of merged bullets, grouped by theme (e.g. "Android release: ...", "Fixed X, Y, and Z") rather than one bullet per commit — roughly 2-5 for a day, 4-8 for a week, and 4-8 for a month (a month covers much more, so pick the highlights rather than trying to fit everything). The existing entries in the file are the pattern to match.

Curate for a public/marketing audience, not a commit log: prioritize what a prospective user would notice (new features, user-facing fixes, platform/support changes). Condense purely internal work (CI/security hardening, code audits, refactors with no user-visible effect) into at most one summarizing bullet per entry rather than enumerating each fix. If covering everything that landed in a period would need more bullets than the cap above, that's a signal to cut to the highlights, not to expand past it.

## Stack

- **Shell**: Tauri 2.0 (Rust backend, `src-tauri/`)
- **Frontend**: SvelteKit (Svelte 5 runes) + TypeScript + Vite, `adapter-static` in SPA mode (`ssr = false` at the root layout)
- **Storage**: SQLite via `tauri-plugin-sql`, fully local — no server, no cloud, no serverless functions in this MVP
- Chosen deliberately over Electron+React Native: Tauri 2 supports Android/iOS from the same codebase. Android is now a real signed release target built on this (see "Android" below); iOS remains not started, kept open by the same choice.

## Run it

```
npm run tauri dev
```

Rust changes trigger a rebuild automatically. Capability/permission JSON changes (`src-tauri/capabilities/*.json`) also require a rebuild to take effect (they're compiled in via `tauri-build`, not read at runtime).

## Core mechanic: wall-clock grid, not a rolling timer

Sessions are pinned to fixed clock boundaries in the user's local timezone, not "25 minutes from whenever the app started":

```
:00–:25 work   :25–:30 break   :30–:55 work   :55–:00 break
```

Implemented as a pure function `grid::slot_for(now) -> Slot` (`src-tauri/src/grid.rs`), unit tested. The scheduler (`run_scheduler` in `src-tauri/src/lib.rs`) computes the exact `Duration` until the next boundary and sleeps precisely to it — no polling loop.

## The overlay and its unlock formula

On entering a break slot, the Rust backend spawns a second Tauri window (label `"overlay"`): fullscreen, undecorated, always-on-top, skip-taskbar — except on macOS, where it's undecorated/always-on-top/skip-taskbar but deliberately **not** real (`.fullscreen(true)`-driven) fullscreen; see the macOS paragraph below for why. Its `close-requested` event is intercepted (`api.prevent_close()`) so Alt+F4 / the close button don't work. On Windows, a low-level keyboard hook (`src-tauri/src/hook.rs`, `WH_KEYBOARD_LL`) also suppresses Alt+Tab and the Windows key while it's open; on Linux, the same file's `linux_impl` does the equivalent via an X11 `XGrabKey` — but only on X11 sessions, since Wayland gives no client a portable way to suppress global shortcuts (a deliberate protocol-level security property, not something this app can work around) — deliberately **not** Ctrl+Shift+Esc or Ctrl+Alt+Del, so Task Manager always stays reachable (see Kill switches below). This is a "strong deterrent, not an absolute lock" by design — Windows won't let an unprivileged app fully block Task Manager without admin/driver-level hooks, which also risks getting flagged as lockdown/malware-like software. `hook::install()`/`uninstall()` run unconditionally regardless of dev mode (see Kill switches #4 below for the dev-testing implication).

**macOS "kiosk mode"** (`src-tauri/src/macos_overlay.rs`) is a structurally different mechanism from the Windows/Linux keyboard hook, not a port of it, and splits into an always-on tier and an opt-in tier:

**The overlay window never uses real macOS fullscreen** (`build_overlay_window` in `overlay.rs` skips `.fullscreen(true)` on this platform specifically) — `macos_overlay::cover_current_monitor` sizes/positions it to the current screen's full bounds instead, called right before `.show()` on every open. This was a real bug, not a theoretical one: real (`toggleFullScreen:`-driven) fullscreen gives a window its own dedicated Space, which fundamentally conflicts with `.canJoinAllSpaces` below (a window can't simultaneously own one dedicated Space and ask to appear in every Space) — the two together left the WindowServer unable to keep the window consistently assigned to any Space, confirmed on a real Mac as: the break screen not appearing on its own at the scheduled boundary, then flashing briefly visible and vanishing again the moment anything forced a re-composite (e.g. bringing the main window forward). A plain borderless window sized to the screen has no such conflict.

- **Always on, no Settings toggle** (dev_mode or not — same tier as always-on-top, which also isn't toggleable):
  - **Accessory activation policy for the duration of a break** (`macos_overlay::enter_accessory_policy`, called in `spawn_or_update_overlay` right before `.show()`; restored to Regular in `exit_kiosk_mode`). Since macOS 10.14, a *regular* (Dock-icon) app's windows can't float over another app's full-screen Space no matter what collection behavior or window level they carry — Electron's `visibleOnFullScreen` works around the same restriction the same way (its `native_window_mac.mm` cites 10.14), and Tauri issue #11488 reports `set_activation_policy(Accessory)` as the fix. This bit for real: a user watching full-screen video saw no break screen for hours even though the log showed every step succeeding (`is_visible=Ok(true)`, collection behavior/level readbacks matching) — it only appeared once they left full screen. Side effect: no Dock icon and no Cmd+Tab entry while a break is open. `configure_window` also calls `orderFrontRegardless` (tao's `show()`/`set_focus()` use `makeKeyAndOrderFront`, which doesn't order front for an inactive app), and `reassert_front_after_delay` repeats that plus an activation request ~1s later, since policy changes reach the WindowServer asynchronously. Both log `isOnActiveSpace` and `app(policy,active)` — `isOnActiveSpace=false` in a user's log is the direct signal this bug is back.
  - `NSWindowCollectionBehavior` (`.canJoinAllSpaces` + `.fullScreenAuxiliary`, plus raising the raw `NSWindow.level` to `NSScreenSaverWindowLevel` — the collection-behavior flag alone doesn't lift a window above a full-screen Space without also raising its level above what Tauri's `.always_on_top(true)` sets) keeps the overlay on whichever Space the user swipes to — over *other apps'* full-screen Spaces only because of the accessory policy above.
  - `NSApplication.presentationOptions.disableProcessSwitching` disables the Cmd+Tab switcher UI. Apple documents presentation options as in effect only "when this app is active", so they do nothing while a full-screen app keeps activation — the other reason for the activation request above.
- **Gated on the `macos_hide_menu_bar_dock_enabled` Settings toggle, off by default** — opt-in, unlike every other enforcement mechanism here, since hiding system UI is a more disruptive change to the user's desktop than anything else this app does: `.hideMenuBar` + `.hideDock`, OR'd into the same `presentationOptions` call as `.disableProcessSwitching` above.

Both tiers are plain, unprivileged AppKit state — no Accessibility permission, no TCC prompt at all. `presentationOptions` and the activation policy are process-global, not per-window, so both are explicitly restored (`macos_overlay::exit_kiosk_mode`, unconditionally clearing every presentation flag back to `.default` and the policy back to Regular) in `close_overlay` — the one function every overlay-close path already funnels through — rather than left to whatever might tear the window down. **Deliberately never sets `.disableForceQuit`**: Activity Monitor/Force Quit is kill switch #1 and must always work, exactly like Task Manager on Windows. Same "deterrent, not lock" tier as everything else here: `.canJoinAllSpaces` makes Mission Control show the window duplicated into every Space's thumbnail (cosmetic only), and an app with true display-capture exclusivity (rare DRM/game cases) can still fully own the screen regardless of collection behavior/level. **`-setPresentationOptions:` only accepts certain flag *combinations*, and an invalid one raises `NSInvalidArgumentException` — which the shipped build cannot catch** (`objc2::exception::catch`'s own docs: it cannot catch anything when compiled `panic = "abort"`, which is what `[profile.release]` sets in Cargo.toml), so a bad combination aborts the entire process rather than just skipping kiosk mode. This bit for real: `.disableProcessSwitching` was being set *on its own* whenever the menu-bar/Dock toggle was off — i.e. in the default configuration — and Apple's Kiosk Mode technote requires that flag to "be accompanied by either `NSApplicationPresentationHideDock` or `NSApplicationPresentationAutoHideDock`". Result on a real Mac: the process aborted at the start of every single break, restart-looping every few seconds, with the log ending at `configure_window`'s line each time (`enable_presentation_lockdown` never reached its own success log). The toggle now selects *which* Dock flag accompanies the always-on Cmd+Tab block rather than whether one is present at all — off (default) → `.disableProcessSwitching | .autoHideDock`, on → `.disableProcessSwitching | .hideDock | .hideMenuBar` (`.hideMenuBar` separately requires `.hideDock`). With the toggle off this costs nothing visible, since the overlay sits at `NSScreenSaverWindowLevel` above the Dock either way. The other documented rules to respect if these flags are ever touched again: `.hideDock` and `.autoHideDock` are mutually exclusive, and `.autoHideMenuBar` needs one of the two Dock flags too. `NSApplicationPresentationFullScreen` is deliberately never set or preserved here (AppKit complains when it's passed with no visible fullscreen window, and the overlay never uses real fullscreen on macOS anyway). The `objc2::exception::catch` wrapper stays as defense-in-depth for dev builds only — the flag rules are the actual safety mechanism.

**Unlock formula** (`OverlayState::unlocked()` in `src-tauri/src/state.rs`), confirmed explicitly with the user and non-obvious from the feature list alone:

```
(time_expired AND reflection_entered) OR (breakit_matched AND reflection_entered)
```

`reflection_entered` (the "what did I do" textarea, submitted) is **always required** — there is no pure-timeout escape. The overlay can, by design, stay open well past the nominal 5-minute break if the user just doesn't reflect. `breakit_matched` is the only early-exit accelerant, and it still requires reflection too.

### breakit: random challenge, not a fixed phrase

Originally designed as a fixed word ("breakit") typed a configurable number of times. **Changed by the user** to: a random string (`src-tauri/src/breakit.rs::generate_challenge`), default 12 characters from a reduced alphanumeric set (`ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz23456789`) that deliberately excludes visually ambiguous characters — `0`/`O` and `1`/`l`/`I` — which render near-identically in several monospace fonts, including the Android overlay's plain `monospace` fallback; optionally also including special characters (`!@#$%^&*()-_=+[]{}`). Generated fresh for every new overlay and shown in the UI. The user must type it exactly (no paste — blocked via `paste`/`drop`/`contextmenu` handlers and Ctrl+V/Shift+Insert interception in the overlay page) to flip `breakit_matched`. Configurable in Settings (`breakit_length`, `breakit_include_special` in `app_setting`, length clamped to `[4, 64]`); being random rather than fixed means it can't become muscle memory.

**Daily cap on successful early-exits** (`breakit_max_per_day` in `app_setting`, default 5, Settings field "Emergency exits per day", clamped to `[1, 100]`) — without this, breakit was a way to skip *every* break's reflection, all day, defeating the app's whole point. Enforced server-side in `commands::breakit_attempt` (not just hidden in the UI), since that command is directly `invoke`-able: only a *successful* code match consumes quota, a wrong guess never does. Usage is tracked in a new `breakit_daily_use` table (see "Data model") rather than in-memory, so restarting the app can't reset the day's count. `breakit_attempt` is `commands.rs`'s one shared choke point for both desktop (invoked directly from `overlay/+page.svelte`) and Android (`native_overlay.rs`'s `BreakitAttempt` event, which has no other path into Rust — see "Android"), so this one check covers both platforms; it's `async` (unlike before) since it now needs a direct DB round trip (`breakit::uses_today`/`increment_daily_use`, via `db::open_direct_pool`) to check/record today's count. Once the day's quota is used up, `OverlayState.breakit_limit_reached` is set — computed once per overlay open (same "checked once at open time" treatment `breakit_challenge` itself gets, in `generate_breakit_challenge`/`breakit_limit_reached_now`, `lib.rs`) — and both overlay UIs (`overlay/+page.svelte`, `native_overlay.html`) hide the code input entirely in favor of a "limit reached, wait for the timer" message; reflection is still required regardless, same as every other path here.

**Cold-start config race**: `AppState.breakit_config` (`src-tauri/src/state.rs`) starts every process at a hardcoded default (length 15, no specials) and only picks up the user's saved values once the frontend's `onMount` gets around to `sync_breakit_config` (`src-tauri/src/commands.rs`) — an async webview-boot + SQLite round trip that a synchronous Rust `.setup()` spawning `run_scheduler` easily wins on a cold start. If `run_scheduler`'s very first loop iteration lands inside an already-live break slot (the common case for Android's `BreakAlarmReceiver` cold-start recovery path — see "Android" below), the challenge generated at that instant used to bake in the default length/charset regardless of what Settings said. Fixed by deferring the *displayed* challenge's generation: `run_scheduler` (`src-tauri/src/lib.rs`) still opens `OverlayState` immediately with a first-pass challenge (preserving the existing "state must be `open` before the warmup await" invariant), but regenerates it from `AppState.breakit_config` a second time right after `overlay::wait_for_webview_warmup` and right before `spawn_or_update_overlay` — the overlay is never shown to the user before that point on any platform, so the regenerated value is what actually gets displayed. Doesn't need to be perfect, only needs to win against the frontend's sync within the ~6s warmup window, which it usually does — but not always: confirmed live on a real device, a cold boot's frontend sync landed at ~7.5s, past the window, still showing the wrong length. Closed properly by `sync_breakit_config` (`src-tauri/src/commands.rs`) itself: whenever it lands while an overlay is already open and not yet solved (`breakit_matched == false`), it regenerates that overlay's challenge in place from the just-synced config and re-emits state, correcting the display however late the sync arrives, independent of the warmup window's timing. The two fixes are complementary, not redundant — the warmup regeneration handles the common case cheaply, this one is the actual close. Lock-ordering note for anyone touching either: `run_scheduler` nests `overlay` then `breakit_config` (holds the overlay lock while calling `generate_breakit_challenge`, which locks `breakit_config`); `sync_breakit_config` must never nest the other way (`breakit_config` held while taking `overlay`), or two threads doing this concurrently deadlock — it releases `breakit_config` before taking `overlay`.

### Reflection field pre-fill

The overlay's reflection textarea pre-fills with the text of the most recently saved reflection (`prefillReflection()` in `src/routes/overlay/+page.svelte`, via `getLastReflectionText` in `src/lib/db.ts`) whenever a new break slot starts and no reflection has been entered for it yet — a UI convenience only, shown with a "Pre-filled with your last entry" hint; nothing is written to the database until the user actually submits.

### "Coming next" preview

Below the submit-reflection button (and below the "Saved" message once it's been submitted), the overlay shows a "Coming next: …" line previewing whatever's already saved for the *upcoming* work slot — the one that begins the moment this break ends — if such a row exists and its text isn't blank or just "skip" (case-insensitively; same check as `import.rs`'s `is_ignorable_entry`). Nothing writes that row ahead of time on the normal path, but the Entries page's bulk edit (see below) or a manual pencil-icon edit can, and this just surfaces it. Shown/hidden entirely — never an empty "Coming next:" line. Desktop (`src/routes/overlay/+page.svelte`) computes it client-side via `nextWorkSlotStartIso`/`getReflectionTextForSlot` in `src/lib/db.ts`, refreshed whenever `current_slot_start` changes. The Android native overlay has no DB access of its own (same constraint as the missed-slot-count heading, see "Inactivity / merge behavior" below), so it's computed once in Rust right before the overlay is shown (`native_overlay::refresh_coming_next_text`, mirroring `refresh_missed_slot_count`), cached in `AppState.coming_next_text`, and read into `native_overlay.html`'s `render()` via `coming_next_text` on every state push. `grid::next_work_slot_start_iso` (Rust) and `nextWorkSlotStartIso` (`db.ts`) are the two independent fixed +5-minute-offset mirrors of each other, the same relationship `preceding_work_slot_start_iso`/`precedingWorkSlotStartIso` already have.

### Bulk-editing reflections by time range

The Entries page (`src/routes/entries/+page.svelte`) has a "Bulk edit reflections" panel above the reflection list, for the day currently selected there (not necessarily today's real date) — set one line of text across every 30-minute work slot that falls *completely* inside a typed HH:MM–HH:MM range in one action, rather than editing rows one at a time via the pencil icon. "Completely inside" matters: for `11:45`–`13:15` only `12:00` and `12:30` qualify (`11:30` starts before the range, `13:00` would end at `13:30`, past it) — computed by `computeBulkEditSlots` in `src/lib/db.ts` via minute-of-day arithmetic (`ceil`/`floor` to the nearest 30), not by walking `Date` objects, to stay correct regardless of timezone offset. It's an upsert per slot (`bulkUpsertReflections`): a slot with an existing row gets its text updated, a slot with none gets a new row inserted (`created_at` shared across the whole batch, same pattern as `saveReflection`). Because this can silently overwrite existing entries, the UI requires an explicit two-step confirm — `previewBulkEditSlots` first reports how many slots are in range and how many already have text that will be replaced, and "Apply" only fires after that preview; changing any field afterward invalidates the stale preview (checked via `bulkFieldsKey()`) rather than letting a second click apply against fields that no longer match it.

**Prefill presets**: a "Prefill" row inside the bulk-edit panel lets the user save the current Start/End/Text fields as a named preset (`bulk_edit_preset` table) and reapply one with a single click instead of retyping the same range for a recurring routine (sleep, lunch, ...). Clicking a preset chip only fills the Start/End/Text fields (still gated behind the existing Preview/Apply confirm step below); an **"Apply all N presets" button** (shown only when there's more than one preset — with just one, it would be redundant with clicking that chip) instead writes every saved preset straight to the DB in one action via `bulkUpsertReflections`, one preset at a time in sequence (`applyAllPresets` in `entries/+page.svelte`) — it bypasses the single-preset fill-then-preview flow entirely (there's only one set of fields, and this is meant to populate a whole day's recurring routine at once), gated behind its own `confirm()` since it can silently overwrite more than the single-preset path ever could; presets are applied in list order, so overlapping ranges between two presets resolve to whichever applied last. Each chip also carries a **checkbox**, independent of the chip's own click-to-fill button, feeding an **"Apply selected (N)" button** next to "Apply all" — same direct-write path (`applyPresetsToDay`, the helper both buttons now share) restricted to whichever presets are checked, for applying a subset (e.g. "Sleep" and "Gym" but not "Lunch" today) without either clicking chips one at a time or running "Apply all" and fixing up the unwanted ones afterward; disabled with nothing checked, and the selection is cleared on a successful apply and pruned of any id that's since been deleted (`loadPresets` intersects it against the freshly-fetched preset list) so it can never point at a preset that no longer exists. v1 is deliberately save/apply/delete only — no in-place edit; changing a preset means deleting it and saving a new one. Two example presets ("Sleep" 00:00–06:00/"Sleeping", "Lunch" 13:00–14:00/"Lunch break") are seeded once via `seedDefaultBulkEditPresetsOnce` (`src/lib/db.ts`, called from `getBulkEditPresets`), gated on an `app_setting` flag (`bulk_edit_presets_seeded`) so it only ever fires once, the same one-shot pattern `ensureFirstRunMarker`/`isOnboardingCompleted` already use. `id` is a client-generated `crypto.randomUUID()`, not an autoincrement integer — it has to stay stable and collision-free across two independent devices for Data export/import and P2P LAN sync to upsert by it, the same reasoning `paired_device.device_id`/`p2p_device_id` already follow. `start_time`/`end_time`/`text` are all ENCRYPTED AT REST like every other user-typed-prose column (see "Encryption at rest" below); `name` stays plaintext since `getBulkEditPresets` sorts by it in SQL, which ciphertext can't support. Participates in Data export/import and P2P sync (see both sections below) as a sixth table, merged by last-write-wins on `updated_at` (`import.rs`'s `import_bulk_edit_presets`) rather than the git-style line merge `reflection`/`daily_task_list` get — a preset's fields are a fixed, atomically-replaced snippet the user explicitly saved, not prose meant to accumulate content from both sides.

### "View all" full-day view

Right after the "Bulk edit reflections" toggle, a "+ View all" button switches the reflection list into a flat, chronological (00:00→23:30 ascending) view of **all 48 work slots for the selected day**, bypassing `clusterReflectionRows`'s clustering/collapsing entirely — every slot gets its own row regardless of whether neighboring slots share identical text. Slots with a saved reflection render exactly as they do in the normal view (same pencil-icon inline edit); slots with none render as a muted "mock" placeholder ("No plan yet") with a `+` control that opens the same inline textarea editor. `getAllSlotStartsForDate` (`src/lib/db.ts`) enumerates the 48 slot starts for a date, mirroring `computeBulkEditSlots`'s `Date`-construction exactly so the ISO strings match what's already in `reflection.slot_start_at`. Saving a mock slot calls the existing `saveReflection` (a single-slot array) — the same plain per-slot upsert the overlay itself uses, not the import.rs line-merge logic — then reloads the day so the slot becomes a real, editable row.

## Inactivity / merge behavior

Because the overlay never auto-closes without a reflection, "what did I do in the last N pomodoros" can end up covering more than one slot. This is **not** special-cased in Rust — the frontend (`src/routes/overlay/+page.svelte`) queries SQLite on mount/update for whether the *previous* break slot's timestamp is already covered by a saved `reflection` row (`isSlotCovered` in `src/lib/db.ts`, a plain `slot_start_at = $1` equality check). If not, `saveReflection` inserts one `reflection` row per covered slot, different `slot_start_at` for each, rather than bundling them into one row. This one check handles both real triggers: the grid reaching the next break boundary while unresolved, and the app being killed/crashed and relaunched with a pending slot.

**Splitting one entry across several missed slots**: when there's more than one covered slot, `saveReflection` (`db.ts`) first tries `splitReflectionForSlots(text, coveredSlots)` — if `text` splits into exactly as many non-blank lines (split on `\n`, trimmed, blank lines dropped) as there are covered slots, each slot gets its own line (index 0 = oldest slot, same oldest-first order `findMissedSlots` already returns), each independently encrypted (genuinely different plaintext per slot now, so each needs its own fresh nonce — see "Encryption at rest"). **Any mismatch in line count falls back to the original behavior**: the same complete `text` written into every covered slot (same `created_at`, one shared ciphertext reused verbatim — safe, since it's one nonce paired with one plaintext copied to several rows, not nonce reuse across different plaintexts). A deliberately-skipped pomodoro inside a split needs the existing `"skip"` convention as that line's content, since a truly blank line doesn't count as a row. The overlay UI (`overlay/+page.svelte`) previews which path will fire, before submit, via a `splitPreview` derived value and a hint line under the heading.

Android's native overlay (see "Android" below) has no DB access of its own, so it can't run this check client-side — `src-tauri/src/native_overlay.rs` mirrors `findMissedSlots`/`saveReflection` **and** the line-splitting logic above in Rust (`find_missed_slots`/`save_reflection`/`split_reflection_for_slots`, byte-for-byte same ISO-string/lookback-cap/line-split logic, unit tested since this file's `#![cfg(target_os = "android")]` gate means it only builds — and its tests only run — on an Android target) and runs it directly against a second SQLite connection at submit time. `native_overlay.html` mirrors the split preview too (`splitHintText`/`updateSplitHint`, live on every keystroke). The heading's "last N pomodoros" wording is likewise mirrored rather than shared: computed once into `AppState.missed_slot_count` right before the overlay is shown (`native_overlay::refresh_missed_slot_count`, called from `overlay::spawn_or_update_overlay`'s Android arm) and read by `native_overlay.html`'s `render()` — since nothing else can write to `reflection` while the overlay has the screen, the count computed at open time is guaranteed to match what `find_missed_slots` recomputes at actual submit time.

## Media pause-on-break

`src-tauri/src/media.rs`, gated on `app_setting.media_pause_on_break_enabled`. Toggled from a button on the **main window** (`src/routes/+page.svelte`, below the Pomodoro mode toggle) — moved out of Settings since it's a frequently-adjusted control, not a one-time preference. Four entirely different mechanisms per platform, all "strong deterrent, not an absolute lock" like the rest of the overlay:

- **Windows**: queries System Media Transport Controls (SMTC) for every registered session and pauses only the ones actually playing (`GlobalSystemMediaTransportControlsSessionManager`). State-aware — never resumes something that was already paused.
- **macOS**: no public API can query playback state the way SMTC does (only the private, undocumented `MediaRemote.framework` can), so this posts a synthetic hardware Play/Pause media-key event instead (`NX_KEYTYPE_PLAY`, via an AppKit `NSEvent` bridge — see `media.rs`'s doc comment for why that needs AppKit and not plain Core Graphics). This is a **blind toggle**: it can incorrectly *resume* media that was already paused before the break started. Explicit, confirmed tradeoff — not a bug. Unlike every other platform, it only works once the user grants Accessibility (post-event) access — see "Permission, macOS only" below. **Before posting, it checks whether any audio output device is running at all** (`any_output_device_running` in `media.rs`: Core Audio's public `kAudioDevicePropertyDeviceIsRunningSomewhere` across every device with output streams, not just the default one, so an app playing to a non-default output still counts; no permission needed). If nothing is running, nothing can be playing, so it skips the toggle rather than risk resuming paused media. It's deliberately one-sided. "Running" doesn't mean "audible": Apple's own forum answer calls it a signal that a device *can* play, reportedly staying true ~30s after pausing, and a call app holding the device open or a duplex USB headset used only for its mic also reads as running (the property isn't scope-aware). All of those just fall back to toggling, the previous behavior. A query failure also toggles (fail open). No reports were found of it reading false while audio actually plays. The key still goes to macOS's single "Now Playing" app, not the frontmost app, so it can hit the wrong player.
- **Linux**: queries MPRIS (Media Player Remote Interfacing Specification, over the session D-Bus) via the `mpris` crate and pauses only players actually playing (`PlaybackStatus::Playing`). State-aware like Windows, not a toggle like macOS — MPRIS doesn't have macOS's private-API wall, so Linux reaches better parity with Windows here than macOS currently can.
- **Android**: no cross-app API exists to list playback sessions and their state the way SMTC/MPRIS do, so this requests transient audio focus (`AudioManager.requestAudioFocus`, `AUDIOFOCUS_GAIN_TRANSIENT`) via the Android bridge (`NativeBridgePlugin.kt::pauseAudioFocus`/`resumeAudioFocus`, called from `media.rs`'s `android_impl` module) instead of a query-then-pause. Any well-behaved playing app receives `AUDIOFOCUS_LOSS_TRANSIENT` and pauses itself per the platform's audio-focus contract. Not a blind toggle like macOS: `close_overlay` abandons the same `AudioFocusRequest` on break-end, which only signals apps that actually ducked for *that* request — it can't resume media that was already paused before the break started.

**Guard, macOS only**: narrows (does not eliminate) the toggle's failure mode for the specific case of "we already toggled it paused this break, and toggling again would resume it" — a relaunch or suspend-resume mid-break re-shows the overlay and would otherwise toggle a second time. Tracks `LAST_MEDIA_TOGGLE_AT` (in-memory, set only when a key is actually posted, persisted to `app_setting.last_toggle_time` via the `media-toggle://recorded` event so it survives a crash/relaunch mid-break) and skips iff it is at or after the current overlay's break-slot start (`already_toggled_this_break` in `media.rs`, parsed RFC3339 instants, not string comparison — the two timestamps carry different offsets). **Replaced an earlier guard** that only reset on a *submitted* wellness check-in (`wellness_check.created_at`, previously confirmed with the user as an accepted tradeoff): a real user's log showed it skipping the pause on every break after one that auto-closed unanswered — a toggle from an early-morning break blocked four breaks that afternoon, since an unanswered break never opens a check-in. Nothing reads `wellness_check` for this anymore.

**Permission, macOS only**: synthetic events posted via `CGEvent::post` are silently dropped by the WindowServer unless the app holds post-event access (its own TCC bucket, `kTCCServicePostEvent`, shown to users under Privacy & Security → Accessibility; checked with `CGPreflightPostEventAccess`). `pause_playing_sessions` checks first and logs a warning plus skips (without recording a toggle) when it's missing. The main window shows a macOS-only "Grant Accessibility access…" button under the media toggle whenever the toggle is on and access is missing (`get_media_key_permission_granted`/`request_media_key_permission` in `commands.rs`), re-checked on window focus; the request calls `CGRequestPostEventAccess` and also opens the Accessibility pane, since TCC only prompts once. The macOS build is unsigned (ad-hoc), and TCC keys grants to code identity, so an update can silently drop the grant — the button reappearing is the expected symptom.

## Screen time tracking

Foreground-app focus tracking -- which app had focus, for how long -- so the Entries tab can show where a day actually went. **On by default** (`app_setting.screen_time_tracking_enabled`, mirrored into `SCREEN_TIME_TRACKING_ENABLED` in `lib.rs` the same way `MEDIA_PAUSE_ON_BREAK_ENABLED` is). `src-tauri/src/screen_time.rs` follows `media.rs`'s shape: one mechanism per platform behind one common interface.

**Windows and Android capture today; macOS/Linux don't yet.** Windows: `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` on its own dedicated thread with its own `GetMessageW` pump -- push-based, no polling -- resolving the exe basename (`chrome.exe`) via `GetWindowThreadProcessId` -> `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` -> `QueryFullProcessImageNameW`. Deliberately a separate thread from `hook.rs`'s keyboard hook (that one's lifecycle is per-break, this one is per-process), and deliberately *not* `WINEVENT_SKIPOWNPROCESS`: the event is wanted when Reflectodoro's own window takes focus too, so the previous app's session gets closed instead of running through the whole break -- a pid check (`pid == std::process::id()`) is what keeps the app out of the user's own breakdown. macOS/Linux are documented no-ops in `platform_impl` for now (planned: `NSWorkspace.didActivateApplicationNotification`, X11 `_NET_ACTIVE_WINDOW` watching with no Wayland equivalent). Everything else below is already platform-agnostic and simply has nothing feeding it there; Settings and the Entries tab both say so explicitly rather than showing an ambiguous "no data".

**Android is the one polling-based platform, not push-based.** No third-party app can get a foreground-focus push without an Accessibility Service, which this app deliberately doesn't use elsewhere and doesn't add just for this — so `screen_time.rs`'s Android `platform_impl` instead polls `UsageStatsManager.queryEvents` on its own `USAGE_POLL_INTERVAL` (5 minutes, deliberately decoupled from `lib.rs`'s unrelated 20s `ANDROID_POLL_INTERVAL` used for break-scheduling Doze-wake correctness — session boundaries come from the OS's own timestamped event log inside each query's result, not from how often the query itself runs, so a coarser interval only delays *when* a session shows up in the flush pipeline, not its recorded accuracy) via a new `NativeBridgePlugin.kt::queryUsageEvents` bridge call. That call returns an ordered stream of foreground-transition events (timestamp + app id, ***not*** pre-paired sessions), which Rust replays through `record_focus_change_at` exactly the way it treats Windows' own `EVENT_SYSTEM_FOREGROUND` callback: each entry closes whatever was open and opens the new one, at that event's own historical timestamp rather than "now." This is deliberately simpler than pairing `MOVE_TO_FOREGROUND`/`MOVE_TO_BACKGROUND` events per package in Kotlin — a background event whose matching foreground event was already consumed by an earlier poll would otherwise have nothing to pair with. An empty `appId` from Kotlin is the "focus left every app" sentinel and covers two cases: Reflectodoro's own process taking foreground (self-exclusion, done by package-name comparison in Kotlin since Android has no pid equivalent exposed to `UsageEvents`), and the screen turning off (`SCREEN_NON_INTERACTIVE`) — without the latter, a session spanning a real suspend would get attributed entirely to whatever app happened to be focused when the screen went dark, the same wrong-attribution problem `SUSPEND_GAP_THRESHOLD` exists to prevent on desktop. The poll loop itself runs unconditionally once installed (matching Windows' hook, which also always runs regardless of the Settings toggle); `record_focus_change_at` is what actually gates on `SCREEN_TIME_TRACKING_ENABLED`, so a disabled period just means replayed events get discarded rather than recorded, not that polling stops.

`queryUsageEvents` owns its own delta cursor, entirely on the Kotlin side, in a plain SharedPreferences key (`reflectodoro_usage_stats`/`last_query_at`) rather than round-tripping through Rust — a process restart resumes from there instead of re-walking (and re-reporting) up to a full day of already-seen history. The cursor only advances when Usage Access is actually granted; left untouched otherwise, so the first poll after the user grants it gets a capped 24-hour lookback rather than silently missing everything that happened before the grant. Requires the special-access **Usage Access** (`PACKAGE_USAGE_STATS`) permission — same tier and same no-in-app-dialog shape as `SYSTEM_ALERT_WINDOW`/`SCHEDULE_EXACT_ALARM`: `can_query_usage_stats`/`request_usage_stats_permission` (Rust) and `canQueryUsageStats`/`requestUsageStatsPermission` (Kotlin) mirror `can_draw_overlays`/`request_draw_overlays_permission` exactly, surfaced as an "Usage access: Granted/Not granted" card in Settings' Screen time section, Android-only, and also offered as its own optional, skippable card on the first-run onboarding screen (`src/routes/onboarding/+page.svelte`) alongside the overlay/exact-alarm/notification grants — same pattern (a status pill plus an "Open settings…" button, re-checked via `visibilitychange` on return), and completing onboarding never requires it. Unlike `ACTION_MANAGE_OVERLAY_PERMISSION`, `ACTION_USAGE_ACCESS_SETTINGS` is not documented to reliably deep-link to this app's specific row via a `package:` data URI on every OEM — `requestUsageStatsPermission` tries the direct form first and falls back to the bare list if the device throws on it; **needs on-device confirmation across OEM skins**, same as exact-alarm's grant screen.

**Friendly display names, Windows only so far**: alongside the stable `app_id` (the exe basename -- `chrome.exe`), `platform_impl` also reads a best-effort `display_name` (e.g. "Google Chrome") from the same exe's `FileDescription` version-resource string, via `version.dll`'s `GetFileVersionInfoW`/`VerQueryValueW` on the already-resolved full path. Purely a label: `app_id` stays the identity/grouping key everywhere (self-exclusion, dedupe, SQL `GROUP BY`), so a missing or empty `FileDescription` (common for console tools/scripts-turned-exe) never breaks anything -- it just leaves `display_name` `""`, and every reader (`getScreenTimeForDate`/`getCurrentScreenTimeSession` in `db.ts`, `entries/+page.svelte`'s rendering) falls back to `app_id` at that point. Resolved once per distinct exe *path* per process lifetime and cached in-memory (`NAME_CACHE`) -- `GetFileVersionInfoW` does real file I/O, and the same handful of apps get focused over and over in a normal day. Android's `queryUsageEvents` does the same thing with its own package-name-keyed cache (`appLabelCache`, via `PackageManager.getApplicationLabel`) — friendly names on Android exist from day one of its capture, unlike Windows where they were added after the fact.

**Reliability note, load-bearing**: `listenForScreenTimeSessionBatches()` is registered in **`+layout.svelte`'s `onMount`, not the home route's `+page.svelte`**. The home route ("/") unmounts on every client-side tab navigation (to Entries, Settings, ...) like any other SvelteKit route, which would tear the listener down with it -- and Tauri's `emit()` returns `Ok` even when nothing is listening (confirmed against the pinned `tauri` version's source), so a batch flushed while the user is sitting on another tab was previously dropped silently and permanently, with no error anywhere and no way to re-request what was lost. `+layout.svelte` is the thing that actually stays mounted across in-window tab navigation, gated on `!isSpecialWindow` so the separate overlay/checkin *windows* (desktop) -- which each run this same root layout in their own webview -- don't also register it and double-save every batch.

**Sessions are buffered in memory and only written when a real app switch closes one** -- never on a timer. `run_flush_loop`'s `FLUSH_INTERVAL` (60s) just ships whatever real switches accumulated as one `"screentime://session-batch"` event; a quiet minute emits nothing and writes nothing. That's the efficiency lever: write *frequency* is capped, write *volume* tracks actual behavior. Three constants shape the rest, all in `screen_time.rs`:
- `MIN_SESSION_DURATION` (5s) -- shorter sessions are dropped as transient-window noise (an alt-tab passed through, a splash screen). A starting guess, not empirically tuned.
- `CHECKPOINT_INTERVAL` (15 min) -- splits an *in-progress* session purely so a hard kill can't lose more than that much of it. Deliberately ~15x coarser than `FLUSH_INTERVAL`: checkpointing every flush tick would write a fresh row every minute for an app the user never switched away from, turning a 3-hour session into ~180 rows instead of 1. It is **not** what keeps the UI's running total accurate -- `get_current_session_snapshot` (a non-writing read of the in-memory current session) is, blended client-side into today's totals by the Entries page.
- `SUSPEND_GAP_THRESHOLD` (120s) -- same idea as `lib.rs`'s constant of the same name, different consequence: `tokio::time::sleep` doesn't advance across a real suspend, so without this a laptop closed for 10 hours with a browser focused wakes up and records a single 10-hour "session" nobody was looking at. On a gap this large the in-flight session is truncated at the last tick's expected wake instant and a fresh one starts at "now".

Nothing here writes SQLite from Rust: batches leave as an event and the **main window** persists them (`listenForScreenTimeSessionBatches` in `db.ts`), same Rust-emits/frontend-writes split as `"media-toggle://recorded"`. That relies on the main window being hidden-not-destroyed on close (`lib.rs`'s `CloseRequested` handler), so its `listen()` registrations keep firing while the app runs tray-only -- **worth verifying on-device**; worst case is delayed, not lost, persistence.

**Where the controls live**: the toggle is in **Settings** (a set-once preference, unlike the frequently-adjusted media-pause toggle, which lives on the main window), alongside a **Device name** text field. `screen_time_session.device_name` exists because `platform` alone would merge "Chrome on laptop A" with "Chrome on laptop B" into one `windows` bucket once Settings -> Data import merges two machines -- the one path data crosses devices in this otherwise single-device app. Seeded once from the OS hostname (`commands::get_hostname`, env/procfs based, no new crate; returns `""` on macOS/Android for now) and renameable afterwards. Never an identity or sync key, so a non-unique or later-changed hostname is harmless.

**The breakdown lives on the existing Entries tab** (`src/routes/entries/+page.svelte`), not a new route: a `.card.screen-time` in the left column below the calendar on desktop (explicit `grid-column`/`grid-row` placement, reset to `auto` under the 600px breakpoint so mobile falls back to DOM order -- calendar, screen time, reflections). It reuses that page's existing `selected`/`selectedStamp` state, so the calendar drives both lists. `getScreenTimeForDate` aggregates per-app totals in SQL (grouped by `COALESCE(NULLIF(app_id_hash, ''), app_id), platform, device_name` -- `app_id_hash` rather than plaintext `app_id`, since `app_id`/`display_name` are encrypted at rest with a fresh nonce every time and never equal themselves twice; see "Encryption at rest"'s "Blind index" paragraph), filed by the local date the session *started* on -- a session crossing midnight counts entirely toward the day it began. One batched decrypt call resolves the handful of distinct apps' `app_id`/`display_name` per day (not one per session row), and a small client-side merge step in `db.ts` collapses the rare case of a legacy still-plaintext group and an already-encrypted group for the same app coexisting during the one-time backfill's transition window. Today additionally blends in `get_current_session_snapshot`, refreshed when the window regains focus rather than on a timer.

**Per-app threshold filter**: apps with less than `app_setting.screen_time_app_threshold_minutes` (default 5, configurable in Settings alongside the tracking toggle) of focus time on the selected day are left out of the Entries tab's list (`visibleScreenTime` in `entries/+page.svelte`) -- a day's tail is usually a long run of apps that briefly had focus for a few seconds. The day's total (`screenTimeTotalMs`) still sums every entry regardless of the filter, so it keeps reading as the whole day rather than just the visible apps; only the per-app list and its bar-scaling max are filtered. Frontend-only (`getScreenTimeAppThresholdMinutes`/`saveScreenTimeAppThresholdMinutes` in `db.ts`), same as `checkin_auto_close_minutes` -- nothing in Rust reads this key, so there's no backend value to sync.

**Only the app's name is ever recorded** -- no window titles, no URLs, nothing typed. Same "never log user content" property the rest of the app has (see "Debugging from production logs").

## Quote API (end-of-break panel)

A small panel at the end of the break overlay's side column shows text fetched from a user-configured HTTP(S) endpoint (`app_setting.quote_api_url`, Settings' "Break screen" card) -- primarily meant for quote APIs, but any endpoint returning short text works. Defaults to `https://zenquotes.io/api/random`, seeded as a real row by `db.rs`'s migration 21 rather than a code-side fallback -- so clearing the field in Settings genuinely disables the panel (blank = off) rather than a hardcoded default fighting the user's choice on the next read. The panel is shown/hidden outright, never an empty box. **Desktop only for now** -- the field is hidden on Android in Settings, and the native overlay (see "Android" below) has no fetch capability of its own; adding it there would mean Rust doing the fetch and pushing the text through `AppState` the same way `coming_next_text`/`missed_slot_count` already are, not yet built.

**This is the app's first outbound call to an arbitrary, user-specified third-party endpoint** -- everything else in this app is either fully local or, for P2P LAN sync, device-to-device with no third party involved. Worth keeping in mind alongside this file's opening "no server or cloud service it depends on" framing (P2P sync being the one other named exception).

The fetch runs in Rust (`commands::fetch_quote`, via a plain `reqwest` client — new dependency, not `tauri-plugin-http`) rather than a webview `fetch()`, for two reasons: many public quote APIs don't send permissive CORS headers, so a browser-side fetch risks being silently blocked even though this app's CSP is null (`tauri.conf.json`'s `security.csp` is `null`); and `tauri-plugin-http`'s capability model expects a fixed URL allowlist in `capabilities/*.json` (already used narrowly for the updater's two hardcoded GitHub domains), which doesn't fit a URL the user can set to anything. A custom Rust command needs no such capability entry beyond the calling window already being in the capability's `"windows"` array (`overlay` already is).

`fetch_quote` rejects non-`http(s)` URLs, uses a 5s timeout, and caps the read to 64KB so a misbehaving endpoint can't balloon memory or wreck the overlay's layout. Parsing is best-effort JSON extraction (`extract_quote_text`, `commands.rs`): tries a handful of common field names (`quote`/`content`/`text`/`message`/`q` for the quote, `author`/`by`/`a` for the author), also unwrapping a single-element array first (covers e.g. zenquotes.io's `[{"q": ..., "a": ...}]`) -- falls back to the raw trimmed response text if the body isn't JSON or matches no known field, truncated to 500 characters. Any error (network, timeout, non-2xx, empty result) is returned to the frontend as `Err`, which the overlay (`src/routes/overlay/+page.svelte`'s `refreshQuote`) treats identically to "feature off": the panel just doesn't render, never a visible error on the break screen, and there's no retry -- one failed attempt just means no quote for that break. A fresh quote is fetched once per break, gated explicitly on `overlayState.open` at both call sites (initial `onMount`'s fallback read and the `overlay://state` listener's slot-change branch, alongside `refreshComingNext`) -- **not** on `current_slot_start` merely changing, since Rust resets that field to `""` both when a break opens *and* when `close_overlay` closes it (`OverlayState::closed()`), and the overlay window is precreated hidden at every app boot regardless of break state. Missing the `open` gate on either call site was a real bug caught in testing: it fetched an extra, useless time on every break-close and on every cold app boot, doubling the effective request rate against whatever (often rate-limited) free API the user configured.

## Encryption at rest

The three columns holding user-typed prose — `reflection.text`, `daily_task_list.content`, `not_to_do_list.content` — are encrypted on disk (`src-tauri/src/crypto.rs`), and so are `wellness_check`'s four boolean columns (`relaxed_eyes`, `exercise`, `drank_water`, `washroom`), each independently as the plain string `"1"`/`"0"`, `screen_time_session`'s `app_id`/`display_name` (its app names — window titles and URLs are never recorded at all, see "Screen time tracking"), and `bulk_edit_preset`'s `start_time`/`end_time`/`text` (see "Bulk-editing reflections by time range"'s "Prefill presets" — `start_time`/`end_time` read like structured data rather than prose, but are encrypted by explicit user choice; `name` is the one column left plaintext there since `getBulkEditPresets` sorts by it in SQL). `screen_time_session.device_name`/`platform` are the one other thing left plaintext (see "Deliberately not encrypted" below). None of these columns is ever filtered/sorted/compared on in SQL, so encrypting them costs nothing in query capability.

**Field encryption, not SQLCipher — and not by preference.** `tauri-plugin-sql` (v2.4.0, confirmed by reading its own `wrapper.rs`) opens its pool with a bare `Pool::connect(url)`: there is no hook to issue the `PRAGMA key` SQLCipher requires immediately after connecting, and no way to pass connect options. Whole-database encryption would mean forking or vendoring the plugin. Field encryption costs nothing in query capability here, because **no code path in this app filters, searches, or sorts on the *value* of those columns** — every `WHERE` is on `id`/`slot_start_at`/`date`/`created_at`/`updated_at`. There is no `LIKE`, no FTS table. (The one value-level comparison, `clusterReflectionRows` in `db.ts`, runs in JS on rows already fetched and decrypted.) If a future feature wants real full-text search over reflections, that constraint is what it will collide with.

**Format**: `enc1:` + base64(`nonce` ‖ `ciphertext` ‖ `tag`), stored in the same existing `TEXT` column — no schema change, no `BLOB` migration. Base64 because the value has to cross Tauri's JSON command IPC (UTF-8 only; raw ciphertext bytes are not valid UTF-8) and tauri-plugin-sql's string bind parameters either way; a `BLOB` column would still need an encoding for the IPC leg, where a `Vec<u8>` serializes *larger* than base64.

**The `enc1:` marker is load-bearing in both directions**: `decrypt` returns anything *without* it untouched, so a row the one-time migration hasn't reached (or one written by an older build) stays readable instead of erroring; and the migration skips anything *with* it, so it can be re-run any number of times without double-encrypting. That per-row check — not the `app_setting.data_encryption_migrated` flag — is what actually makes the migration idempotent; the flag is only a "don't rescan every launch" shortcut.

**Nonces are always freshly random, never derived from another column.** Not a style choice: `updateReflectionText`, `bulkUpsertReflections`, and `import.rs`'s merge-then-`UPDATE` all rewrite `text` for the *same* `id`/`slot_start_at`, so a nonce derived from either would repeat across genuinely different plaintexts under one key — the failure that leaks the XOR of both plaintexts and, under GCM, the authentication key itself. This app also ships a **plaintext export**, which hands an attacker ready-made known-plaintext to pair against a stolen ciphertext DB, making nonce reuse worse here than in the abstract. XChaCha20-Poly1305 (192-bit nonce) was chosen over AES-256-GCM (96-bit) precisely so "generate a fresh random nonce every time" is safe at any volume with no counter shared between the several independent callers (`commands.rs` for db.ts, `import.rs`, `native_overlay.rs`).

**Blind index: `screen_time_session.app_id_hash`.** `app_id`/`display_name` use the same random-nonce scheme as everything else above, which means (by design) the same app name never encrypts to the same value twice — but `getScreenTimeForDate` (`db.ts`) needs to `GROUP BY` app identity to produce daily per-app totals, and `import.rs`'s `import_screen_time_sessions` needs an equality check to dedupe a re-imported file, and neither can run against ciphertext that never repeats. `app_id_hash` is a deterministic HMAC-SHA256 of the plaintext `app_id`, computed and stored alongside the ciphertext (`FieldCipher::blind_index_many`) purely so SQL can group/compare on *that* column instead. It is never used to recover the plaintext — HMAC isn't reversible — only to tell "these two rows are the same app" apart from "different apps". A single deterministic cipher on `app_id` itself (AES-SIV or similar) would give the same equality-leaks-but-names-don't property in one column instead of two, but was rejected: the Android Keystore has no SIV mode, so it would mean hand-rolling and independently verifying a second cipher scheme rather than reusing proven primitives (the existing AEAD cipher plus a standard HMAC) on both platforms.
  - **Key**: never the raw AEAD key reused as a MAC key — that's a key-separation anti-pattern. Desktop derives a dedicated subkey via HKDF-SHA256 from the raw 32-byte key (`BLIND_INDEX_HKDF_INFO` in `crypto.rs`), since Rust holds that key directly there. Android's Keystore key is non-exportable — there is no raw key in Rust to derive from — so Android instead generates a second, independent Keystore key for this (`HMAC_KEY_ALIAS`/`hmacFields` in `NativeBridgePlugin.kt`, `KEY_ALGORITHM_HMAC_SHA256`/`PURPOSE_SIGN`). The two platforms arrive at "a device-local HMAC key distinct from the AEAD key" through different mechanisms, but both output base64 HMAC-SHA256, so the on-disk format is identical.
  - **Device-local, by construction, not by convention**: since each device already generates its own AEAD key independently and never exchanges it (see "Key storage" below and P2P sync's device-local keys), the derived/generated HMAC key differs per device too — `HMAC(deviceA_key, "chrome.exe")` and `HMAC(deviceB_key, "chrome.exe")` never match. P2P sync never sends `app_id_hash` for this reason (`build_delta_payload` decrypts `app_id`/`display_name` for the wire like every other encrypted column, but leaves the hash out entirely); the receiver computes its own via `import_screen_time_sessions`.
  - **Accepted leak**: unlike the three prose columns and `wellness_check`'s booleans, `screen_time_session` trades away part of the "ciphertext reveals nothing" property on purpose. Anyone who steals `pomodoro.db` without the encryption key can still tell that two rows share an app (matching `app_id_hash`) and infer usage frequency per app — they cannot recover the app's name. This is the deliberate cost of keeping the daily-aggregation query and the import duplicate check running in SQL on a table documented as likely to become the largest by row count, rather than decrypting every row to group/compare in application code.
  - **Migration**: `crypto::migrate_screen_time_sessions_once`, gated on its own `app_setting.screen_time_encryption_migrated` flag — deliberately *not* folded into `MIGRATED_KEY`/`ENCRYPTED_COLUMNS` above, since an install that already ran that migration before this feature shipped has `MIGRATED_KEY = "true"` and would otherwise skip this table's backfill outright. Selects `WHERE app_id_hash = ''` in chunks (`SCREEN_TIME_MIGRATION_CHUNK`, 500 rows), each chunk its own transaction, so a crash mid-backfill leaves already-committed rows fully encrypted+hashed and the rest untouched plaintext — never a row with ciphertext but no hash, which is what makes re-running it safe.

**Key storage, per platform** — and the honest threat model, which differs a lot by OS:
- **Windows / Linux**: `keyring` crate (Credential Manager / Secret Service). Neither OS meaningfully isolates one desktop app's stored secret from another process running as the same user, so this mainly protects a *cold* copy of the data — a stolen or imaged disk, a backup folder synced to the cloud, another OS account — **not** a live session where something else is already running as you.
- **macOS**: Keychain does enforce real per-app ACLs, but they're keyed to code identity and this build is unsigned/ad-hoc, so a rebuild can drop the grant exactly the way the media-key TCC grant already does (see "Media pause-on-break"). The file fallback below is what keeps that from becoming a hard failure.
- **Android**: the strongest of the four. The key is a non-exportable Android Keystore key — another app cannot read it even on an unlocked device. Because Keystore keys can't be exported, the AES-256-GCM operation itself happens in Kotlin (`NativeBridgePlugin.kt`'s `encryptFields`/`decryptFields`), not Rust; Rust only ever names the key by alias. Deliberately **not** `setUserAuthenticationRequired(true)`: breaks fire on a schedule while the device may be locked and backgrounded, and a key needing an unlock first would leave the overlay unable to read or write a reflection exactly then.
- **Fallback, desktop only**: if the OS store is unreachable *or demonstrably not persisting*, a random key file in `app_config_dir()` (`0600` on Unix) is used instead, and the app logs a warning. The persistence check is not paranoia — `keyring` v3 has **no default features** and a build that names no backend silently falls back to an *in-memory mock store*, which here would mean a fresh key every launch and every already-encrypted row becoming permanently unreadable. `crypto.rs` therefore writes a new key, reads it back through a *fresh* `Entry`, and only trusts the store if the value survives. Cargo.toml names the backend explicitly per platform (`windows-native` / `apple-native` / `sync-secret-service` + `crypto-rust`); the Linux one needs `libdbus-1-dev` at build time, added to `release.yml`'s install list.

**Migration of pre-existing rows**: `crypto::run_encryption_migration_after_db_ready`, spawned from `setup()` with the same 10×750ms retry loop `p2p_sync::get_or_create_device_id_after_db_ready` uses, for the same cold-start reason (`.setup()` runs before the frontend's `Database.load()` has necessarily created the db or applied migrations). Runs in one transaction. **Deliberately does not touch `updated_at`** on rows it rewrites: that column is P2P sync's delta cursor, and re-encrypting is a storage-format change, not a content edit — bumping it would make every paired device re-send its whole history. If it never succeeds in a session that's safe, not a data hazard: new writes are encrypted regardless, unmigrated rows stay readable via the marker passthrough, and the next launch retries.

**Where encrypt/decrypt happen** — four independent call sites, all going through `crypto::FieldCipher` (resolved once per batch, since a key fetch is a D-Bus round trip on Linux and a JNI hop on Android):
- `db.ts` — via the batched `encrypt_fields`/`decrypt_fields` commands. Batched because the read side is list-shaped (a day's Entries view decrypts up to 48 rows; an export decrypts everything) and each `invoke` is its own IPC round trip. No key material ever reaches the webview. `getWellnessSummaryForDate` is the one place this batching is load-bearing rather than just an optimization: it used to let SQLite `SUM`/`COUNT` the four booleans directly, which ciphertext broke, so it now fetches every matching day's rows, decrypts all four columns in one batched call, and sums client-side instead — still cheap at a day's scale (≤48 rows).
- `import.rs` — the git-style line merge for reflections/task lists can't compare lines it can't read, so existing rows are decrypted in, merged, and re-encrypted out. `import_wellness_checks`' merge never reads the boolean *values* (its dedupe keys on `created_at` alone), so it only ever encrypts-on-insert, for whichever row wins the per-slot dedupe. `import_screen_time_sessions` hashes and encrypts every incoming row up front (never a decrypt pass first — incoming rows are always plaintext, see below) and compares on `app_id_hash` rather than `app_id` for its duplicate check. Incoming rows are always plaintext whichever caller it is (a file import's JSON is plaintext by design; a P2P payload was decrypted by the sender).
- `p2p_sync.rs` — `build_delta_payload` decrypts before sending, for all four synced tables' encrypted content (the three text columns and wellness_check's four booleans). The two devices in a pair hold **entirely unrelated keys** (each is device-local and never exchanged), so the payload travels plaintext *inside* the Noise session that already encrypts and authenticates the whole transfer, and the receiver re-encrypts under its own key via `import.rs`. Shipping raw ciphertext would be unreadable garbage on the far end.
- `native_overlay.rs` (Android) — its direct-to-SQLite reads/writes. On an encrypt failure it deliberately **does not** mark the reflection as entered (that's what unlocks the overlay), rather than unlocking over a save that didn't happen or silently degrading to writing plaintext. Never touches `wellness_check`: the check-in popup is a normal SvelteKit route that runs in the main webview on Android too (unlike the break overlay itself), so it already goes through `db.ts`'s command-based path above.

**Deliberately not encrypted:**
- **The export file** (Settings → Data → Export) stays plain JSON. It's a portability format meant to be re-imported on another device holding an unrelated key, so ciphertext would make it unreadable everywhere. Encryption protects the live `pomodoro.db`; a file the user explicitly chose to write somewhere is their call. `exportAllData` decrypts on the way out. This is also why `wellness_check` (see below) was fine to encrypt despite shipping a plaintext export: the frequency-analysis worry about encrypting a 2-value field doesn't apply to randomized AEAD anyway — a fresh random nonce makes `"1"`/`"0"` ciphertexts indistinguishable regardless of plaintext entropy — but a plaintext export is still ready-made known-plaintext for anyone pairing it against a stolen ciphertext DB, same reasoning as the "Nonces are always freshly random" paragraph above.
- **`screen_time_session.device_name`/`platform`** stay plaintext. Every row written by one device shares the same `device_name` value and the same handful of `platform` values app-wide, so encrypting either would cost real complexity (both are also used for `GROUP BY` and the import dedupe key) for very little privacy gain — unlike `app_id`, there's no meaningful "which app" secret being hidden, just "which device/OS", already visible from context (Settings shows the device name in plain sight) and from the shape of the data itself.

`wellness_check`'s four booleans used to be deferred here too — its `SUM`/`COUNT` SQL aggregation (`getWellnessSummaryForDate`) couldn't run over ciphertext — but that aggregation now happens app-side (decrypt-then-sum, batched) instead, so all four columns are encrypted like everything else above. Migration 23 (`db.rs`) changed the columns from `INTEGER` to `TEXT` to hold ciphertext; `crypto.rs`'s `ENCRYPTED_COLUMNS` migrates each of the four independently (four `(table, "id", column)` entries against one row, since every other encrypted table has just one value column per row).

`screen_time_session.app_id`/`display_name` were likewise deferred for a while — see the "Blind index" paragraph above for how `getScreenTimeForDate`'s `GROUP BY` and `import.rs`'s duplicate check keep working now that they're ciphertext. Migration 24 (`db.rs`) added `app_id_hash` and rebuilt `idx_screen_time_session_dedupe` to key on it instead of plaintext `app_id`; the now-useless plain `app_id` index (migration 13) was dropped.

## Data model

No `pomodoro_session` table — deliberately. Slot identity/boundaries are fully determined by computing from a timestamp against the fixed grid, so there's nothing session-shaped to persist.

```sql

  created_at TEXT
```

Migrations live in `src-tauri/src/db.rs` (`tauri-plugin-sql` migration list). Applied versions are tracked per-database in `_sqlx_migrations` and never re-run — so editing an already-shipped migration silently skips on any db that already applied it. Before the first tagged release, squashing/rewriting migrations freely is fine (nothing but local dev dbs has run them). From the first tagged release onward, always add a new versioned migration for schema/default changes instead.

**On-disk location** (Tauri's `app_config_dir()`, identifier `com.reflectodoro.app` from `tauri.conf.json`) — useful for inspecting `pomodoro.db` directly with the `sqlite3` CLI when diagnosing a silent write/migration issue (see "Known gotchas" below):
- Windows: `%APPDATA%\com.reflectodoro.app\pomodoro.db`
- macOS: `~/Library/Application Support/com.reflectodoro.app/pomodoro.db`
- Linux: `~/.config/com.reflectodoro.app/pomodoro.db`
- Android: app-private storage, not directly browsable without root/debug tooling (`run-as com.reflectodoro.app` via `adb shell`)

### Data export/import

Settings → Data lets the user export the whole DB to JSON and re-import it (`exportAllData`/`parseAndValidateExport`/`importData` in `src/lib/db.ts`). Validation (JSON shape, per-table field types, no-duplicate-PK within the file) stays entirely client-side in `parseAndValidateExport` before anything is written. Execution itself is a single Tauri command, `import_data` (`src-tauri/src/import.rs`), run inside one real `sqlx` transaction on a second, direct connection to `pomodoro.db` (`db::open_direct_pool` — the same "open a second connection because tauri-plugin-sql's own pool isn't part of its public API" pattern `native_overlay.rs` already uses for Android, just not platform-gated here) — `tx.commit()` only at the very end, so a mid-import failure rolls back everything rather than leaving the DB partially written. This replaced an earlier, non-atomic version that sent statements through tauri-plugin-sql's own `execute()`, which doesn't guarantee consecutive calls land on the same underlying SQLite connection.

**"Merge" mode does a real git-style line merge per reflection slot, not a blind append.** For every `slot_start_at` in the imported file, `import.rs` combines the existing DB row(s) for that slot with the imported row(s) for that slot into one surviving row: split both sides' `text` into trimmed, non-blank lines; if the imported side has any line that isn't literally "skip" (case-insensitive), any existing "Skip" placeholder line is dropped (real content having arrived means the placeholder no longer applies); then every incoming line gets appended unless it's already present case-insensitively. Any *other* pre-existing duplicate rows for that slot (there's no `UNIQUE` constraint stopping them) get collapsed into the same survivor too. "Replace" mode wipes the affected tables first, so there's nothing to merge against — every imported reflection row just inserts fresh (still going through the same collapsing logic, which is a no-op with an empty existing-side).

**An imported row that's skip/empty-only is dropped before any of the above** (`is_ignorable_entry` in `import.rs`): if a row's `text`, once split and trimmed, reduces to nothing or to nothing but "skip" lines, it's excluded entirely from slot-grouping — it can't touch an existing row (no "Skip" line gets appended to real content) and can't seed a brand-new row on its own. Applies in both import modes, since there's no reason to persist a placeholder-only row on a fresh insert either.

**`wellness_check` dedupes/collapses on `slot_start_at` too** (`import_wellness_checks` in `import.rs`), keeping exactly one row per slot: whichever of the existing DB row(s) and the imported row(s) for that slot has the earliest `created_at` survives; everything else for that slot — other pre-existing duplicates, every other imported row — is deleted/skipped. A tie favors the existing row over a pointless delete+reinsert. Like the reflection collapse, this only visits slots that actually appear in the imported file; a slot with pre-existing duplicates but nothing incoming for it isn't touched. This is also *why* `wellness_check.reflection_id` was replaced with `slot_start_at` (migration 17) rather than just adding `slot_start_at` alongside it: keying off the same natural identity every other table here uses means this dedupe needs no id-map/FK-remap step at all, unlike the old `reflection_id`-based version.

**`screen_time_session` also dedupes on import** (`import_screen_time_sessions` in `import.rs`): a row whose `(app_id, platform, device_name, started_at, ended_at)` already exists is skipped rather than inserted again — `display_name` is deliberately excluded from that key, since it's a display-only label, not part of a session's identity (see "Screen time tracking" above). Implemented as a plain `INSERT ... WHERE NOT EXISTS` rather than a `UNIQUE` constraint + `INSERT OR IGNORE`, so it doesn't require a backfill migration to dedupe rows a pre-fix double-import may already have written, and doesn't constrain `screen_time.rs`'s normal capture-write path at all — only import goes through this check. `idx_screen_time_session_dedupe` (`db.rs` migration 16, non-unique) is what keeps the `NOT EXISTS` lookup fast on this table, which is documented above as likely to become the largest by row count. Applies in both modes (harmless in "replace" mode, since the table was just wiped).

**`daily_task_list`/`not_to_do_list` get the same git-style line merge as reflections, minus the "skip" rule** (`merge_import_day_rows` in `import.rs`, sharing `append_unique_lines_ci` with `merge_reflection_lines`): in merge mode, a day that already has content gets it combined with the imported day's content line-by-line — existing lines kept in place, any imported line not already present (case-insensitively) appended after them — rather than the import blindly overwriting the day's text. Both tables are keyed by a real `PRIMARY KEY` (`date`), so unlike `reflection`/`wellness_check` there's never a duplicate-row-collapsing step needed here, just a per-day upsert (`INSERT ... ON CONFLICT(date) DO UPDATE`). `app_setting` is the one table left where merge mode is genuinely "imported wins on conflict" — a plain value, not a line-based list, so there's nothing to merge.

**`bulk_edit_preset` merges last-write-wins by `updated_at`, not a line merge or a natural-key dedupe** (`import_bulk_edit_presets` in `import.rs`): keyed directly by its client-generated `id` (see "Bulk-editing reflections by time range"'s "Prefill presets"), an `INSERT ... ON CONFLICT(id) DO UPDATE ... WHERE excluded.updated_at > bulk_edit_preset.updated_at` either inserts a new preset, overwrites an older one, or is a no-op when the existing row is already at least as new. `ImportResult.bulkEditPresetStaleCount` reports how many imported rows lost that comparison, mirroring the other tables' duplicate/overwrite counts. "Replace" mode wipes the table first, same as every other content table.

## P2P LAN sync

Manual by default, device-to-device sync over the local network — Settings' "Paired devices" card (pairing, the paired-device list, "Import from device") and, for the manual Sync button and per-device status, also the home window (see "Home-screen widget and per-device auto-sync" below). No server, no relay, no third party ever sees anything: two devices on the same wifi connect directly to each other. `src-tauri/src/p2p_sync.rs` has the full design in its module doc comment (security model, wire protocol); this section is the app-level summary.

**Pairing is PIN-based, but the PIN is never the encryption key.** A 6-digit PIN authenticates a SPAKE2 password-authenticated key exchange (`spake2` crate) that derives a full ~256-bit shared key — that key, not the PIN or a hash of it, is what encrypts everything afterward (`snow` crate, Noise `NNpsk0`). This matters because "hash the PIN, use it as a key" would let anyone who merely *records* the pairing handshake brute-force a 6-digit PIN offline in seconds; SPAKE2's guarantee is that a passive eavesdropper learns nothing usable that way — every guess needs to actively interact with one of the two real devices. The residual risk (someone on the LAN guessing PINs live against an open pairing window) is closed by a hard attempt limit (`MAX_PAIRING_ATTEMPTS`, 5) plus a short window (`PAIRING_WINDOW`, 60s) — a handful of guesses, then the session must be reopened. The Noise handshake right after SPAKE2 doubles as key confirmation: a wrong PIN makes the two sides derive different keys, so the Noise handshake's AEAD authentication fails outright rather than silently succeeding with mismatched keys.

**Discovery**: mDNS (`_reflectodoro._tcp.local.`), advertising `device_id`/`name`/`platform` in the TXT record — never the shared key or any content. Desktop uses the pure-Rust `mdns-sd` crate directly; Android has no portable Rust mDNS, so it goes through `NsdManager` instead, bridged the same way every other Android-only capability here is (`NativeBridgePlugin.kt`'s `registerP2pService`/`unregisterP2pService`/`discoverP2pServices`, wrapped by `android_bridge.rs`). The TCP pairing/sync connection itself (`tokio::net`) and the crypto (`spake2`/`snow`) are identical on every platform — only discovery is platform-gated.

`name` is a real device name where the platform supports reading one: Windows uses `COMPUTERNAME`, Android reads `Settings.Global.DEVICE_NAME` (falling back to `Build.MODEL`) via `NativeBridgePlugin.kt::getDeviceName` — `commands::get_hostname` has a dedicated Android arm for this now, confirmed live rather than always returning `""` the way it used to. `name` and `device_id` are otherwise unrelated: `device_id` (a random 128-bit value, `p2p_sync::get_or_create_device_id`) is the only thing pairing/sync actually key off, so a spoofed or duplicate `name` can cause user confusion in the pairing candidate list but can't bypass the SPAKE2/Noise authentication — completing a pairing or sync still requires the real PIN or the real `shared_key`, neither of which `name` has any bearing on.

**Sync is bidirectional and always "merge" mode, never "replace"** — one "Sync" click both sends this device's changes since the pair's last successful sync and applies whatever the other device sends back, reusing `import.rs`'s existing merge functions (`import_reflections`, `import_wellness_checks`, `merge_import_day_rows`, `import_screen_time_sessions`, `import_bulk_edit_presets`, all made `pub(crate)` for this) rather than duplicating merge logic. This is safe because that merge logic is already additive everywhere it matters: `daily_task_list`/`not_to_do_list` do a git-style line merge, not overwrite; `reflection`/`wellness_check`/`screen_time_session` dedupe by natural key rather than losing rows; and `bulk_edit_preset` merges last-write-wins by `updated_at` keyed on its own cross-device-stable `id` — running it from both sides carries no more risk than running the existing manual "Merge" file import twice. **`app_setting` is never part of the payload in either direction** — settings stay strictly per-device, unlike the file-based export/import's "include settings" toggle. `SyncResult` reports both directions separately (`sentCount` alongside the existing received-row counts) — a sync that only moved data outward (this device had a new change, the peer had nothing new to send back) used to report "0 rows" and read as a no-op even though it worked; confirmed as real user confusion in live testing before this was added.

**Delta cursor**: each `paired_device` row tracks its own `last_sync_at` (see "Data model"). `reflection` needed a new `updated_at` column (migration 19) since it previously had no way to tell a post-insert edit apart from the original insert; the other five synced tables already had a usable column (`daily_task_list`/`not_to_do_list.updated_at`, `screen_time_session.started_at`, `wellness_check.created_at` — both append-only — and `bulk_edit_preset.updated_at`, which doubles as its LWW merge key). The cursor is captured (`sync_started_at`) *before* querying deltas and only advances to that captured value after a successful sync — not to "now" after the transfer completes — so nothing created mid-transfer is missed on the next sync, same snapshot-then-query pattern the file-based export already uses.

**Wire protocol**: one TCP connection (port `p2p_sync::PORT`, 47811) per pairing attempt or sync session, u32-be length-prefixed frames throughout. A leading tag byte picks pairing vs. sync, so one listener (spawned once at startup, `run_listener`) handles both. Everything past the SPAKE2 exchange (which is deliberately sent in the clear — that's the whole point of a PAKE) is Noise-encrypted; a sync payload larger than Noise's single-message ceiling is chunked into multiple encrypted frames (`send_encrypted_json`/`recv_encrypted_json`). `run_listener` binds **both** IPv4 (`0.0.0.0`) and IPv6 (`[::]`) — confirmed live that a peer resolved via mDNS can come back as either family, sometimes for the *same* device across two separate browses (an mDNS responder can answer with a global IPv6 address, not just a LAN-scoped one), and an IPv4-only listener silently refused any connection that landed on the IPv6 address that round. `browse_lan`'s desktop arm also prefers IPv4 when a peer offers both, for the same reason.

**Two cold-start races, both fixed after showing up in live two-device testing** (a real timing/ordering bug a unit test can't reproduce, since it depends on exactly how fast the frontend boots relative to Rust's synchronous `.setup()`):
- `advertise_self` runs synchronously from `.setup()`, before `pomodoro.db` necessarily exists yet (the file/migrations only get created once the frontend's `Database.load()` actually runs) — its `device_id` lookup used to fail outright with `SQLITE_CANTOPEN` on a cold start. Fixed with `get_or_create_device_id_after_db_ready` (10 retries, 750ms apart).
- The same race hits `device_name`: `advertise_self` reads it before the frontend's `ensureDeviceName()` (an async round trip) has written anything, so the very first LAN advertisement showed a blank name even once Android could capture a real one. Unlike the `device_id` case there's nothing to retry-into-existence here (the name genuinely doesn't exist yet), so this is fixed differently: both `advertise_self` variants are idempotent (unregister-before-register), and a new `resync_advertised_name` command re-advertises on demand — called from `saveDeviceName` (db.ts), covering both `ensureDeviceName`'s cold-start auto-seed and a manual rename in Settings, neither of which previously reached already-advertising peers without an app restart.

### Home-screen widget and per-device auto-sync

The **home window** (`src/routes/+page.svelte`) shows its own "Paired devices" card — a `.paired-devices-card` at the bottom of the page, hidden entirely (never an empty state) when nothing's paired yet — listing every paired device with its online/offline status, a manual "Sync" button (identical behavior to Settings' own, just a separate copy of `runDeviceSync`/state, not shared), and a per-device **Auto-sync** checkbox. This exists so syncing (and opting a device into automatic sync) doesn't require a trip to Settings; Settings' own paired-device rows keep the same checkbox too, both writing through the same `set_device_auto_sync_enabled` command, so either page reflects the other's changes on next load.

**Auto-sync is a per-device opt-in, not a global toggle** — `paired_device.auto_sync_enabled` (migration 27, `INTEGER NOT NULL DEFAULT 0`), local to each side's own copy of the pairing record like `last_sync_at` already is, and **never** part of the sync payload (a device's own opt-in choice has no bearing on its peer's). Defaults off, matching this feature's existing "manual, opt-in" framing — auto-sync transmits reflection/task-list content over the network with zero interaction, closer in disruptiveness to `MACOS_HIDE_MENU_BAR_DOCK_ENABLED` (also opt-in, off by default) than to this app's ordinary on-by-default toggles.

**Trigger, deliberately not a new background loop, foreground service, or wake lock** — `p2p_sync::maybe_auto_sync` piggybacks entirely on wake-ups the app already incurs:
- **Primary**: `run_scheduler`'s break-boundary phase transition (`lib.rs`). Hooked at the *transition check itself* (`if last_phase != Some(slot.phase)`), not inside the nested `if POMODORO_ENABLED { ... }` block the rest of `Phase::Break` handling lives in — so turning Pomodoro mode off doesn't also silently disable auto-sync. Fired via `tauri::async_runtime::spawn` (fire-and-forget) so a slow/stuck sync attempt can never delay the overlay opening. Fires exactly once per break boundary on both desktop (precise sleep-to-boundary) and Android (the existing `ANDROID_POLL_INTERVAL` wall-clock re-check, itself woken by `AlarmManager.setAlarmClock` — infrastructure that exists purely for break scheduling and costs nothing extra here).
- **Secondary**: the main window regaining focus, reusing `+page.svelte`'s pre-existing `onWindowFocus` handler (previously only used to re-check the macOS media-key permission) — covers a desktop user who does one work session and closes the app before ever reaching a break. A thin `attempt_auto_sync` command spawns the same `maybe_auto_sync` and returns immediately.

**Battery cost is gated in three steps, each cheaper than the last is common**: `maybe_auto_sync` first runs `SELECT EXISTS(SELECT 1 FROM paired_device WHERE auto_sync_enabled = 1)` — a local SQLite read only, no network activity at all — and returns immediately if nothing is opted in, so a process with auto-sync off everywhere pays only that cost on every break boundary/focus event. Only once something *is* opted in does it call `get_paired_devices` (the same bounded local-multicast mDNS browse Settings' "Import from device" already performs) to find out who's online. Only a device that's online, opted in, and past a `MIN_AUTO_SYNC_GAP` (10 minutes, per device, keyed off `last_sync_at`) actually gets a real sync attempt (`sync_with_device` — the same TCP+Noise dialer path the manual button uses). The 10-minute throttle exists for the edge cases that can re-trigger the phase-transition branch within seconds of a previous evaluation — a snooze expiring mid-Break or the suspend/hibernate-gap recovery path both reset `last_phase = None` — not against the normal ~25-30 minute break cadence, which wouldn't double-fire on its own.

A completed auto-sync emits `p2p-sync://auto-completed` (device_id payload) so both the home widget and Settings' list can refresh their `last_sync_at`/online display without the user doing anything; `sync_with_device`'s own logging already covers the attempt/outcome, so this event is purely a "please refetch" signal, not a data channel.

## Kill switches (must always work, tested explicitly)

These are desktop-specific (Windows/macOS/Linux); Android has no tray, no `Alt+F4`-style close, and no global-shortcut plugin (see "Android" below) — its enforcement relies on the OS's own notification/overlay-permission controls instead.

1. **Task Manager** (Ctrl+Shift+Esc on Windows; Activity Monitor / Cmd+Option+Esc Force Quit on macOS) — never blocked, by design.
2. **Tray → Quit** — `std::process::exit(0)`, deliberately *not* `app.exit()` or a window `.close()`, so it can't get caught by the overlay's close-requested prevention.
3. **Ctrl+Alt+Shift+F12** (Windows/Linux) / **Cmd+Option+Shift+F12** (macOS) — global shortcut, force-destroys the overlay, registered unconditionally (not just in dev builds). Platform-selected at runtime via `cfg!(target_os = "macos")` in `setup_dev_kill_switch` (`src-tauri/src/lib.rs`); the Settings UI label is driven by the `current_os` command so it always matches what's actually registered.
4. **Dev mode** (`cfg!(debug_assertions)` by default, override with `POMODORO_DEV_MODE=0/1`): shows a visible "Close (DEV)" button on the overlay. The Alt-Tab/Win-key/Cmd-Tab suppression hooks (`hook::install()`, and macOS kiosk mode's always-on tier) install unconditionally regardless of dev mode — dev and release builds now behave identically there — so the "Close (DEV)" button plus kill switch #3 (F12) are the way to escape the overlay while testing locally.
5. **Desktop-only: the reflection-save escape hatch.** If `saveReflection`/`mark_reflection_entered` fails twice in a row for the current overlay occurrence (a locked or full DB, most concretely), the overlay reveals a "Close break screen anyway" button (`src/routes/overlay/+page.svelte`). It calls `close_after_save_failure` (`commands.rs`), which is gated server-side on `OverlayState.save_failure_count` actually having reached that threshold — not reachable by a single direct `invoke` call the way `mark_reflection_entered` is, though (like every other command here) it's not a real boundary against a devtools-capable user. Exists so a genuinely broken DB write can't leave the user with no way out short of #1-#4 above; behaves like a force-close (no reflection recorded, no check-in opens).

## Android

Android is a real, signed release target, not experimental scaffolding — `src-tauri/gen/android/` is fully generated and committed, with custom Kotlin sources beyond the Tauri template. Because the generated Android WebView shell doesn't get the same low-level window control as desktop (no separate undecorated always-on-top window, no `WH_KEYBOARD_LL`-style hook), break enforcement is implemented natively rather than by reusing the desktop overlay window:

- **Native overlay + notification fallback**: `NativeOverlayManager.kt` draws a system overlay over other apps when the user has granted "Display over other apps" permission (`canDrawOverlays`/`requestDrawOverlaysPermission`, exposed via `NativeBridgePlugin.kt`); without that permission it falls back to a break notification instead.
- **`NativeBridgePlugin.kt`** (`src-tauri/gen/android/app/src/main/java/com/reflectodoro/app/`, a `@TauriPlugin`) is the Rust↔Kotlin bridge, wrapped on the Rust side by `src-tauri/src/android_bridge.rs::AndroidBridge<Wry>`. It exposes `ping`, `startForegroundService`/`stopForegroundService`, `triggerBreakScreen`, `cancelBreakNotification`, `updateNativeOverlay`, `initNativeOverlayChannel`, `canDrawOverlays`/`requestDrawOverlaysPermission`, `canScheduleExactAlarms`/`requestScheduleExactAlarmPermission`, `pauseAudioFocus`/`resumeAudioFocus` (see "Media pause-on-break" above), `canQueryUsageStats`/`requestUsageStatsPermission`/`queryUsageEvents` (Usage Access grant + polling for screen time tracking, see "Screen time tracking" above), and `registerP2pService`/`unregisterP2pService`/`discoverP2pServices` (`NsdManager`-backed LAN discovery for P2P sync, see "P2P LAN sync" below — `ACCESS_WIFI_STATE`/`CHANGE_WIFI_MULTICAST_STATE` declared in the manifest for this).
- **Scheduling survives process death and reboot**: `BreakSchedulerService.kt` runs as a foreground service; `BreakScheduling.kt` independently mirrors the `grid::slot_for` boundary rule in Kotlin to compute the next wake time via `AlarmManager.setAlarmClock` — deliberately *not* `setExactAndAllowWhileIdle`, since only `setAlarmClock` is exempt from Android 10+ background-activity-launch restrictions (confirmed on-device). Side effect: a persistent alarm-clock icon in the status bar whenever Pomodoro mode is on. AOSP docs describe `setAlarmClock` as exempt from the Android 12+ `SCHEDULE_EXACT_ALARM` permission requirement entirely, but that's been disproven on a real device (a HONOR/MagicOS Android 12 unit threw a `SecurityException` from it, crashing the app on every launch) — so `scheduleNextAlarm` now gates the call on `AlarmManager.canScheduleExactAlarms()` and falls back to a plain inexact `alarmManager.set()` (losing the foreground-launch exemption, but not crashing) when it isn't granted. `SCHEDULE_EXACT_ALARM` is declared in the manifest, and onboarding (`src/routes/onboarding/+page.svelte`) and Settings both surface a grant/re-check card for it, mirroring the overlay-permission one. `BootCompletedReceiver.kt` restarts the scheduler service on `ACTION_BOOT_COMPLETED` — this is Android's own reboot-recovery mechanism and is unrelated to the desktop login-item autostart below. Pomodoro-mode-enabled state itself still isn't persisted in Rust's `POMODORO_ENABLED` (it resets to its default of `true` on every fresh process start, same as desktop), but `commands::set_enabled` also mirrors the toggle into a plain Android `SharedPreferences` flag (`NativeBridgePlugin.kt::persistPomodoroEnabled`) purely so this receiver — which runs before any Tauri/Rust runtime exists in a freshly booted process — has something to check first; `BootCompletedReceiver` reads it (`PomodoroEnabledPref.isEnabled`, defaulting to enabled) and skips restarting the service entirely for a user who had deliberately turned Pomodoro mode off. The main window's Pomodoro dropdown adds a third option alongside On/Off: a **snooze** (`commands::snooze_pomodoro`, 30/60/120/360/720 min, in-memory `POMODORO_SNOOZE_UNTIL_MS`/`POMODORO_SNOOZE_MINUTES`) that pauses Pomodoro mode temporarily and auto-resumes on its own — checked by wall-clock comparison inside `run_scheduler`'s own loop (deliberately not a `tokio::time::sleep`-based timer, which would be `Instant`/`CLOCK_MONOTONIC`-based and could fire late across a real suspend, the same class of bug `ANDROID_POLL_INTERVAL` below exists to work around; `sleep_dur` is capped to a 30s `SNOOZE_POLL_INTERVAL` on every platform, not just Android, whenever a snooze is pending, so this poll actually runs often enough). Unlike a permanent Off, a snooze deliberately never calls `stop_foreground_service` — that call is what lets Android reclaim (kill) the process while backgrounded, which would leave nothing running to notice the snooze expire — and it persists the `PomodoroEnabledPref` boot-recovery flag as `true` rather than mirroring the in-memory `false`, since the durable preference is meant to stay "on" through a transient pause. **The resume-at timestamp (and the originally chosen duration) are also persisted** (`NativeBridgePlugin.kt::persistPomodoroSnoozeUntil`/`getPersistedPomodoroSnoozeUntil`, a `Long` + an `Int` in the same `reflectodoro_prefs` file as `PomodoroEnabledPref` — see `PomodoroEnabledPref.getSnoozeUntilMs`/`getSnoozeMinutes` in `BootCompletedReceiver.kt`) — this exists because a foreground-service process is not actually immune to being killed: several OEM skins kill it outright when the user swipes the app from Recent Apps, which used to silently reset `POMODORO_ENABLED`/`POMODORO_SNOOZE_UNTIL_MS` back to their Rust defaults on the next launch and cancel the pause with no warning. Rust's `setup()` reads this back (before `run_scheduler` is spawned) on every fresh process start: a still-future timestamp restores both the paused atomic and the resume time, a stale one (already passed while the process was dead) just gets cleared. The duration is persisted alongside the timestamp, not just the timestamp alone — the main window's dropdown selects its displayed `<option>` off `SnoozeInfo.minutes`, and an early version of this fix restored only `until_ms`, leaving `POMODORO_SNOOZE_MINUTES` at its default `0` after a restore; `0` matches none of the dropdown's fixed option values, so the control rendered with nothing selected (blank) even though the pause itself was still correctly in effect. `apply_pomodoro_enabled` clears the persisted value on every manual On/Off and on the scheduler's own auto-resume, so a cancelled snooze can't be resurrected by a later relaunch. Known accepted limitation, narrower than before: if the process is killed and never relaunched before the resume time passes, nothing proactively flips `POMODORO_ENABLED` back to `true` — that only happens lazily, the next time something does relaunch the process (mirrors the same "reboot mid-snooze" case this paragraph used to describe as entirely unhandled). `BreakAlarmReceiver`'s own "was the scheduler already running" check (`MainActivity.isSchedulerAlive()`) is a genuine liveness signal, not a one-time flag: `run_scheduler` reports a heartbeat (`reportSchedulerHeartbeat`) on every loop iteration (at least every `ANDROID_POLL_INTERVAL`), so a scheduler task that dies without taking the whole process down with it is still detected as dead rather than being permanently mistaken for alive because *some* Activity existed once.
- **`POST_NOTIFICATIONS`** (denied by default on API 33+; without it, the break notification and the process-recovery wake notification both silently don't show) is requested through `@tauri-apps/plugin-notification`'s own `isPermissionGranted`/`requestPermission` JS API — deliberately *not* a custom `NativeBridgePlugin.kt` command the way the overlay/exact-alarm grants are, since the standard plugin already handles this runtime permission correctly. Onboarding offers the grant on first run; Settings mirrors it with its own check/request pair (same `isAndroid`-gated card pattern as the overlay/exact-alarm/persistent-notification controls) for anyone who skipped it there or revoked it later.
- **A second, direct SQLite connection on Android only**: the native overlay is a plain WebView with no Tauri IPC bridge, so it needs its own path to write a reflection row directly from Rust. `Cargo.toml`'s `[target.'cfg(target_os = "android")'.dependencies]` pulls in `sqlx` for this.
- **`android:allowBackup="false"`** (`AndroidManifest.xml`) is explicit, not left at the platform default (`true`) — this app is "fully local, single-device" by design (see the top of this file), and `pomodoro.db` is the entire reason that matters: every reflection ever written. Auto Backup would otherwise silently upload it to the user's Google Drive and restore it onto any device signed into that account.
- **Break-end detection polls wall-clock time on Android**: `run_scheduler` (`src-tauri/src/lib.rs`) normally waits for the next grid boundary with a single `tokio::time::sleep`, which schedules against `Instant`/`CLOCK_MONOTONIC` — a clock that does not advance while the CPU is actually suspended (unlike `CLOCK_BOOTTIME`). A break spanning a real Doze/deep-suspend period could leave that sleep never firing at the right wall-clock instant, since `BreakAlarmReceiver`'s `AlarmManager.setAlarmClock` chain only guarantees a brief wake window, not one long enough for a large monotonic deficit to fully elapse — symptom: a reflection submitted mid-break, but the overlay never auto-closes once time is actually up. `ANDROID_POLL_INTERVAL` (20s) caps each sleep on Android so the loop re-checks `grid::slot_for(Local::now())` from the wall clock frequently instead, self-correcting on whatever brief wake windows the alarm chain provides. Desktop doesn't need this for the same wake-cadence reason — an actual laptop suspend is instead caught by `SUSPEND_GAP_THRESHOLD` (`lib.rs`) once its single long sleep does eventually return. That threshold (120s) only governs re-evaluating the current phase, though; whether an *unresolved* overlay actually gets force-closed after a suspend gap is separately bounded by `OVERLAY_AUTO_CLOSE_MINUTES` (the same user-configured grace period `schedule_auto_close` applies to an ordinary unresolved break) — same rule on both platforms now, so a suspend can't force-close on a shorter fuse than just sitting at the desk not responding would. `OVERLAY_AUTO_CLOSE_MINUTES` and the check-in window's own `checkin_auto_close_minutes` are both clamped to `[1, 60]` (Rust's `set_overlay_auto_close_minutes` and the Settings page for both) — an unbounded value would otherwise defeat the documented last-resort force-close outright (`u32::MAX` minutes), and on the check-in side a large-enough value silently fires its plain JS `setTimeout` *immediately* instead of waiting, since it wraps past `setTimeout`'s ~24.8-day (2³¹ ms) ceiling.
- **The native overlay carries its own wall-clock watchdog, independent of the Rust channel**: `NativeOverlayManager.kt`'s `show()` schedules a fixed 20-minute self-removal (`WATCHDOG_TIMEOUT_MS`) the moment the WindowManager view is added, checked by instance identity so it can't tear down a later break's overlay. It deliberately does not go through `overlayChannel`/`native_overlay.rs::install_channel` to trigger this — if that channel setup silently failed (every `OverlayJsBridge` method becomes a no-op in that case), routing the watchdog through the same broken channel would be defeated by the exact failure it exists to guard against. Rust's `OverlayState` never learns this fired (no reflection submitted, no check-in opens), same as any other force-close with nothing submitted.
- **Desktop-only plugins are excluded on mobile**: `tauri-plugin-global-shortcut`, `tauri-plugin-autostart`, `tauri-plugin-updater`, `tauri-plugin-process`, and `tauri-plugin-single-instance` are all gated out via `[target.'cfg(not(any(target_os = "android", target_os = "ios")))'.dependencies]` in `Cargo.toml`. So desktop login-item autostart (`commands.rs::set_autostart_enabled`, which returns "not supported on this platform" off-desktop) and the Ctrl+Alt+Shift+F12 kill switch have no Android equivalent — `settings/+page.svelte` hides the force-close-shortcut section on Android (`isAndroid`) and instead shows Android-only controls for the overlay-permission, exact-alarm-permission, and persistent-break-notification settings. `about/+page.svelte`'s "Check for updates" button is gated the same way (`current_os` → `isAndroid`), since calling the excluded updater plugin's `check()` throws `"updater.check not allowed. Plugin not found"` at runtime rather than failing at build time — the static JS import itself doesn't error, only invoking it does.
- **Signed CI releases**: `.github/workflows/release.yml`'s `android` job sets up JDK 17 + the Android SDK/NDK, decodes a signing keystore from the `ANDROID_KEYSTORE_BASE64` secret, runs `npm run tauri android build -- --apk --split-per-abi --target aarch64 armv7`, and uploads signed release APKs to the GitHub Release. It also runs a separate `npm run tauri android build -- --aab --target aarch64 armv7` (deliberately *not* `--split-per-abi` — Play's own dynamic delivery does per-device ABI splitting from one universal bundle, so splitting here too would just duplicate shared assets across modules) and uploads the resulting `.aab` to the same GitHub Release, verified signed via `jarsigner -verify` first since Gradle's bundle task — unlike the APK task — doesn't name an unsigned output differently. This only gets the bundle onto the GitHub Release alongside the APKs; actual Play Console submission (upload, track selection, rollout) is still a manual step, not yet wired into CI.
- **iOS has none of the above** — it's excluded from the same Cargo `cfg` groups as Android but has zero implementation behind it. "Planned but not yet started" (the phrase this doc used to apply to Android as a whole) is accurate only for iOS now.

## Debugging from production logs

`tauri-plugin-log` is wired up in `lib.rs`'s `run()` with three targets — `Stdout`, `LogDir`, and `Webview` (the last one mirrors frontend `@tauri-apps/plugin-log` calls into the same file too, useful since the hidden overlay/checkin windows have no devtools window open by default) — filtered to `log::LevelFilter::Info`, so `log::info!`/`warn!`/`error!` all persist; `debug!`/`trace!` do not. This means a real installed build (not just `npm run tauri dev`) already writes a durable log file, which matters a lot when a bug only reproduces on a device you don't have physical/remote access to (e.g. reported by someone else testing a release build).

**Log file location** (`LogDir` resolves to Tauri's `app_log_dir()` — note this is a *different* base directory than `app_config_dir()`, which is where the SQLite db's "On-disk location" above lives; don't assume they share a parent folder). The current file is `Reflectodoro.log` inside that directory (rotated backups are named `Reflectodoro_<timestamp>.log`) —
- Windows: `%LOCALAPPDATA%\com.reflectodoro.app\logs\Reflectodoro.log` (Local, not Roaming/`%APPDATA%` — that's where the db lives instead)
- macOS: `~/Library/Logs/com.reflectodoro.app/Reflectodoro.log`
- Linux: `~/.local/share/com.reflectodoro.app/logs/Reflectodoro.log` (`$XDG_DATA_HOME` if set, not `~/.config` — that's where the db lives instead)
- Android: app-private storage, same `run-as`/adb caveat as the db.

**Rotation**: explicitly set to `RotationStrategy::KeepSome(10)` + `max_file_size(50_000)` (50KB) — deliberately overriding the plugin's own defaults (`KeepOne` + 40KB), which would otherwise silently destroy old logs rather than archive them: per the plugin's own source, `KeepOne` doesn't keep one rotated *copy*, it **deletes** the active file outright once it hits the size cap and starts a fresh empty one. At the default 40KB, ordinary Info-level logging (a phase transition + breakit challenge every ~25min, plus the macOS overlay path's logging) could fill and wipe the file in about a day of normal use -- exactly the kind of gap that would defeat asking someone else for "the log from when it happened" a day or two later. With the current settings, once the active file exceeds 50KB (roughly a day of normal-use logging) it's renamed to a dated archive (`Reflectodoro_<timestamp>.log`) instead of deleted, and up to 10 such archives are kept before the oldest is finally removed — small enough per-file that a single log file can be pasted whole into a conversation, and 11 files at this cap span roughly 1-2 weeks of retained history.

When asking someone else to help diagnose a bug they hit (rather than you), the log file from around the time it happened is usually more useful than a description of what they saw — ask for it (or the last screenful of it) before guessing from symptoms alone.

**None of the user's actual content is ever logged** — reflection text, wellness check-in answers, and Most Important Tasks / Not-To-Do list content all flow straight from the frontend (or, on Android, `native_overlay.rs`) into SQLite via `sqlx`/`tauri-plugin-sql` bind parameters, never through a `log::`/`@tauri-apps/plugin-log` call. `breakit_challenge` used to be a documented exception — `overlay::emit_state` and `lib.rs`'s `generate_breakit_challenge` both logged its actual value at Info level, on the reasoning that it's just a random on-screen string the user retypes, not private input — **removed**: neither call site logs the challenge's value *or* its length anymore (only `cfg.length`/`cfg.include_special`, the configured settings, and — in `emit_state` — `open`/`slot`). There's no remaining diagnostic reason to log anything challenge-derived: the cold-start-race bug class this used to help debug (see "Cold-start config race" above) is fully covered by the settings values already logged. This matters because the log file is routinely handed to someone else for diagnosis (see "Exporting logs from the UI" below) — it's safe to share without redaction, full stop, with no remaining exception.

**Exporting logs from the UI**: the About page's "Logs" section (`src/routes/about/+page.svelte`) gives a non-technical user a way to hand over logs without knowing any of the OS-specific paths above. "Export last log file…" copies just the active `Reflectodoro.log`; "Export last N log files as .zip" (`N` clamped to `[1, 11]` in the UI — one more than `RotationStrategy::KeepSome(10)` keeps, so the max covers everything on disk) zips the N most recently modified `*.log` files in the log directory into one archive. Both go through the native save dialog first, then `log_export.rs`'s `export_last_log_file`/`export_log_archive` commands — plain `std::fs` (plus the `zip` crate for the archive case) rather than tauri-plugin-fs, same reasoning and same `.log`/`.zip`-extension-check mitigation as `commands::read_text_file`/`write_text_file`'s doc comment. `log_files_newest_first` sorts by file *modified time* rather than parsing the `{name}_{date}.log` archive-naming convention, so it doesn't need to track that format if the plugin's naming ever changes.

**Silently-discarded `Result`s are the recurring way real bugs here go unlogged** — `let _ = win.show()`/`win.set_focus()`/etc. throws away exactly the information you'd need if that call ever actually failed. `overlay.rs`'s `spawn_or_update_overlay` and `open_main_window` (`lib.rs`) both learned this the hard way and now log every step of showing a window (entry visibility check, the show/focus calls' own `Result`s, post-show visibility) rather than discarding them — worth matching that pattern (log both the attempt and its outcome, not just failures) in any new code that drives window/OS state changes, since those are exactly the class of thing that fails silently and differently on a machine you can't get onto.

## Known gotchas already hit in this codebase

- **`sql:default` (tauri-plugin-sql) does not include `execute`** — only `select`/`load`/`close`. Every INSERT/UPDATE needs the capability to also list `sql:allow-execute` explicitly, or writes silently no-op with no visible error.
- **Every window label needs to be in a capability's `"windows"` array, or it gets zero permissions** — not reduced, zero, including for the app's own custom commands. The default Tauri template scopes `capabilities/*.json` to `["main"]` only; the dynamically-created `"overlay"` window had to be added explicitly (`src-tauri/capabilities/default.json`).

Both bugs were silent (no thrown error visible to the user) — diagnosed by querying the SQLite file directly with the `sqlite3` CLI to confirm writes weren't landing, then reading the plugin's actual `permissions/*.toml` from the cargo registry source rather than assuming from memory.

- **Linux tray icon needs a desktop-environment extension to appear at all** — vanilla GNOME (especially under Wayland) has no tray/status-icon area by default; it requires the "AppIndicator and KStatusNotifierItem Support" extension. KDE and XFCE show the tray icon out of the box. Nothing in `setup_tray` (`src-tauri/src/lib.rs`) can fix this from the app side — it's a desktop-environment configuration gap, not a bug.
- **macOS: a window can't simultaneously own a dedicated Space (real `.fullscreen(true)`/`toggleFullScreen:`) and ask to join every Space (`NSWindowCollectionBehavior::CanJoinAllSpaces`)** — setting both left the WindowServer unable to keep the overlay consistently assigned to any Space: it didn't appear at the scheduled break boundary, then flashed briefly visible and vanished again on any forced re-composite (e.g. bringing the main window forward). Diagnosed without access to the reporting device, from `tao`'s (Tauri's window backend) own source confirming `.fullscreen(true)` invokes real `toggleFullScreen:` on macOS, not a plain resize. Fixed by never using real fullscreen for the overlay on macOS (`macos_overlay::cover_current_monitor` substitutes a borderless window sized to the screen instead) — see "The overlay and its unlock formula" above.
- **macOS: a regular (Dock-icon) app's windows can't appear over another app's full-screen Space, whatever their collection behavior or level** (restricted since macOS 10.14), and every AppKit readback still reports success — `is_visible` true, level/collection behavior matching. Reported from a remote user's log: a full-screen video hid every break screen for an afternoon. Fixed by switching the process to the accessory activation policy while a break is open. The same log also showed the media toggle skipped on almost every break by its old check-in-based guard. See "The overlay and its unlock formula" and "Media pause-on-break" above.
- **Windows: the main window's countdown could freeze (stale time, not updating) after a break ended**, most visibly right after the check-in window closed and "main" became visible again. Root cause is Chromium's Windows-only native window occlusion tracker (`CalculateNativeWinOcclusion`): it marks a window "occluded" and throttles its renderer/timers, same treatment as a backgrounded tab, whenever another window fully covers it on screen — which is exactly what happens to "main" for the whole break+check-in duration, since the overlay is always-on-top/fullscreen and the check-in popup after it is always-on-top/maximized. Distinct from the solid-white swapchain-loss bug below (that one needs a monitor power-cycle; this one just needs an ordinary break to run with another window on top of "main" the whole time). Fixed the same way, in the same place: `--disable-features=CalculateNativeWinOcclusion` added alongside `--disable-gpu` in the `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` set in `run()` (`src-tauri/src/lib.rs`).
- **Windows: WebView2's GPU-accelerated compositor loses its DirectX swapchain when the physical display powers off** (monitor sleep/blank) and never requests a repaint when the display comes back, leaving any visible webview (most consequentially the break overlay, which is meant to be inescapable) solid white until something else forces a repaint. Fixed by disabling WebView2 GPU acceleration process-wide (`--disable-gpu`, same `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` set as above) — must be set before the first `WebviewWindow` is built, since WebView2 only reads it when its environment is created.
- **The desktop overlay's clock/countdown (`src/routes/overlay/+page.svelte`) could show stale time the moment a break opened** -- two distinct causes, both in `onMount`. (1) The overlay window is precreated once and reused for every break (`onMount` runs exactly once per app process), so `tickInterval`'s `setInterval` also only starts once; it used to start *after* `await refreshQuote()`, which hits a user-configured endpoint with a 5s timeout -- if that one `onMount` run happened to land inside an already-open break (e.g. app relaunched mid-break), a slow/unreachable quote endpoint delayed the first tick by up to 5s. Fixed by starting `tickInterval` immediately after the fallback `get_overlay_state` invoke, before `refreshQuote`. (2) Independent of that, the overlay sits `hidden` between breaks (up to 25 minutes) -- long enough for Chromium/WebKit's background timer throttling to slow `nowTick`'s interval well below 1/sec while hidden, so the *first* render after the window is shown could reflect a stale `nowTick` until the throttled interval caught up. Fixed by explicitly resyncing `nowTick = Date.now()` the instant `overlayState.open` flips true (both in the `overlay://state` listener and, implicitly, via the reordered interval start above) rather than relying solely on the interval's own cadence. Android's native overlay (`native_overlay.html`) never had this staleness problem in the first place -- its `renderClock()` reads a fresh `new Date()` on every tick rather than a cached state variable, so a throttled/delayed tick there just shows the correct time a beat late, never a stale one.
- **The same "interval started after a long await chain" pattern also hit the main window's clock/countdown (`src/routes/+page.svelte`)**, with tab navigation as the trigger instead of a slow quote fetch: the home route (`"/"`) unmounts on every client-side tab navigation and remounts when the user comes back to it (see "Screen time tracking"'s reliability note for why), re-running `onMount` -- and `bootMainWindow()`'s ~9-step sequential-awaited-IPC boot chain -- on every such visit. `tickInterval` used to only start at the very end of that chain, so `now` (initialized once at component creation) sat frozen at its pre-remount value for however long the chain took, on every switch back to the Home tab -- plus, if `bootMainWindow` ever threw partway through (already handled/logged, see the comment above it), the interval never started at all and the clock stayed frozen for the rest of that mount. Fixed the same way as the overlay: `tickInterval` now starts (with an explicit `now = new Date()` resync first) at the top of `onMount`, before `bootMainWindow` runs, so it can't be delayed or skipped by anything in that chain.
- **Android: Play Console needs native debug symbols, which `strip = true` was throwing away at compile time.** `Cargo.toml`'s `[profile.release]` uses `strip = "debuginfo"` (keeps the symbol table, drops full DWARF) rather than `true`, and `src-tauri/gen/android/app/build.gradle.kts`'s `release` build type sets `ndk.debugSymbolLevel = "SYMBOL_TABLE"` so AGP packages that symbol table into the `.aab`'s debug-symbols bundle metadata — stripped back out of the actual APK Play serves to devices, so this costs nothing in what users download on Android. Since `[profile.release]` is shared by every platform, this does add a small amount of symbol data to the Windows/macOS/Linux release binaries too (a deliberate, accepted trade-off — `FULL`-level symbols were rejected specifically because Rust's monomorphization makes full DWARF debug info large enough to meaningfully bloat desktop binaries, which have no Android-style re-strip-before-serving step). Don't casually revert `strip` back to `true` without checking this note first.

## Not built yet / explicitly deferred

- Cross-network sync (two devices not on the same LAN, or not simultaneously online) and any form of account/cloud service — still deferred by user decision. Manual same-LAN P2P sync (see "P2P LAN sync" below) covers the same-wifi case; if cross-network sync is ever revisited, the recommended direction (not designed in detail) is an end-to-end-encrypted, short-TTL serverless mailbox rather than a permanent central DB.
- **P2P LAN sync has been verified live on one real device pair (a Windows desktop and one Android phone)** — pairing, bidirectional sync, and the mDNS/NSD discovery paths on both sides all completed successfully, and that testing is what surfaced and got fixes for the dual-stack listener bug, both cold-start races, the sent-row-count reporting bug, and the blank/oversized Android device-name issues documented above. **Not yet verified**: macOS or Linux as either side of a pair, more than two devices/more than one paired peer at once, and a real cross-subnet or VPN-adjacent network (the live testing incidentally surfaced that a Tailscale virtual interface on the Windows machine logs harmless `mdns_sd` multicast-send errors every browse cycle — noisy but not something that broke pairing/sync in testing, not yet root-caused or silenced).
- Configurable work/break durations (currently fixed 25/5 constants).
- iOS builds — Android ships as a signed release APK already (see "Android" above); iOS has no implementation at all yet, only `cfg` exclusions alongside Android's.
- **Wayland Alt-Tab/Win-key-equivalent suppression** — `hook.rs`'s `linux_impl` implements real suppression via `XGrabKey`, but only on X11 sessions (detected at runtime via `XDG_SESSION_TYPE`/`WAYLAND_DISPLAY`). Wayland sessions get a no-op, deliberately: no client can suppress global shortcuts under Wayland by design, so an X11-only implementation is the ceiling here, not a gap to fast-follow on — unlike macOS's Cmd+Tab suppression (see "The overlay and its unlock formula"), which *is* built and always on; there's no Wayland equivalent to build at all. Same "deterrent, not the lock itself" reasoning applies regardless.
- **State-aware macOS media pause** — `src-tauri/src/media.rs` pauses media on Windows (via SMTC) and Linux (via MPRIS) with true query-then-pause, but the macOS path is a best-effort toggle (see "Media pause-on-break" below). A state-aware macOS implementation is possible later via the private, undocumented `MediaRemote.framework` (the technique tools like `nowplaying-cli` use), which would eliminate the toggle's known limitation — not built yet: real scope (a new Rust module) and depends on an API Apple could change without notice.
- **macOS code signing / notarization** — no Apple Developer account yet, so the macOS build is unsigned. Gatekeeper blocks it on first launch (see README's workaround). Revisit if/when an account is obtained; the release pipeline (`.github/workflows/release.yml`) is structured so signing env vars can be added to the macOS matrix leg without restructuring it.
- **Screen time capture on macOS and Linux** -- the whole feature (buffering, flushing, storage, Settings toggle, Entries breakdown) is platform-agnostic and shipping, and now captures on both Windows and Android; only macOS/Linux capture remains unbuilt. See "Screen time tracking" for each platform's planned mechanism.
- **Friendly app names for screen time, on macOS/Linux** -- Windows resolves a `FileDescription`-based `display_name` and Android resolves one via `PackageManager.getApplicationLabel` (see "Screen time tracking"); macOS/Linux fall back to their raw identifier (bundle id / WM_CLASS) until their capture mechanisms are built at all. No icon mapping anywhere yet, on any platform. Related known gap, Windows-specific: a UWP/packaged app's foreground window can resolve to `ApplicationFrameHost.exe` (both `app_id` and `display_name`) rather than the real app.
- **Browser tab/site-level screen time** -- app-level granularity only; "which site" would need per-browser extensions or accessibility APIs, deliberately out of scope.
- **Encryption at rest is verified on Windows and compile-checked for Android, but not yet confirmed on a real device for macOS, Linux, or Android.** Specifically unverified: macOS Keychain behavior under an unsigned build (the ACL-drops-on-rebuild case), Linux Secret Service presence and the key-file fallback path, and Android's Keystore `encryptFields`/`decryptFields` bridge on real hardware. Same "needs on-device confirmation" tier as the exact-alarm and Usage Access grants before them. The `screen_time_session.app_id_hash` blind index adds one more Android-specific thing to confirm on real hardware: `NativeBridgePlugin.kt`'s second Keystore key (`HMAC_KEY_ALIAS`, `KEY_ALGORITHM_HMAC_SHA256`) and its `hmacFields` bridge call are compile-checked only, same as the AES key/`encryptFields` were before their own on-device confirmation.
- **Screen time retention/pruning** -- `screen_time_session` is likely to become the largest table by row count within weeks, and both the export file and a `replace`-mode import grow with it. No auto-prune, no export-exclusion toggle yet.
- **Idle/locked-screen detection** -- a session keeps accruing while the machine is merely idle or locked (Win+L) with a window focused; only a real *suspend* is caught (see `SUSPEND_GAP_THRESHOLD` in `screen_time.rs`).
- **Linux `.deb`/`.rpm` packages** — the Linux release deliberately ships AppImage only (`src-tauri/tauri.linux.conf.json`). `tauri-plugin-updater` only auto-updates AppImage on Linux, so adding deb/rpm would need a separate, unsigned distribution/update story via system package managers before it's worth doing — not a technical blocker, just undone.
- **Quote API panel on Android** — see "Quote API (end-of-break panel)" above; shipped on the desktop overlay only. The Android native overlay has no fetch capability of its own, so this would need Rust to fetch and push the text through `AppState` the same way `coming_next_text` already works — not yet built, and the Settings field is hidden on Android in the meantime.
